# 비주얼리 재방문 구조 Usecase

> Version: v0.2
> Updated: OAuth 로그인 후 결과 복구, `/my` empty state, 체크인 예외 흐름, Phase 1 범위 명확화, RLS 완료 기준을 보강했다.

## 1. 문서 목적

이 문서는 비주얼리를 기존의 1회성 스킨케어 진단 서비스에서, 사용자가 반복적으로 방문해 자신의 피부 상태와 루틴을 점검하는 **피부 루틴 관리 플랫폼**으로 확장하기 위한 Usecase 정의서다.

Codex는 이 문서를 기준으로 로그인, 결과 저장, 마이페이지, 오늘 피부 체크, 루틴 카드, 제품 관리, SOS, 주간 리포트 기능을 단계적으로 구현한다.

단, Phase 1에서는 재방문 루프의 최소 핵심인 **결과 저장 → `/my` → 오늘 체크인 → 오늘 루틴 카드**까지만 구현한다. `user_products`, `sos_logs`, `weekly_reports` 관련 기능은 Phase 2 이후로 미룬다.

---

## 2. 제품 방향

### 기존 구조

```txt
방문
→ 사진 업로드
→ 설문 입력
→ 무료 결과 확인
→ 유료 리포트 확인 또는 이탈
```

현재 구조는 사용자가 한 번 진단을 받고 나면 다시 방문할 이유가 약하다. 화장품 추천 서비스는 기본적으로 구매 전후 특정 시점에만 사용되는 경향이 있기 때문에, 재방문 루프를 별도로 설계해야 한다.

### 확장 방향

```txt
1회성 진단키트
→ 내 피부 프로필 저장
→ 오늘 피부 상태 체크
→ 오늘 루틴 조정
→ 내 제품 조합 점검
→ 피부 SOS 대응
→ 주간 피부 리포트
```

비주얼리의 중심은 단순 제품 추천이 아니라 **오늘 내 피부 상태에 맞게 루틴을 조정해주는 서비스**가 되어야 한다.

---

## 3. 핵심 목표

> Note: 아래 핵심 목표와 로그인 사용자 가능 행동은 전체 제품 로드맵 기준이다. Phase 1 구현 범위는 Section 8과 Section 10.7을 우선한다.

- 최초 진단 결과를 사용자 계정에 저장한다.
- 로그인 사용자는 자신의 피부 프로필을 다시 확인할 수 있다.
- 사용자는 매일 또는 필요할 때 피부 상태를 체크할 수 있다.
- 체크인 결과에 따라 오늘의 AM/PM 루틴을 조정한다.
- 사용자는 현재 사용 중인 제품을 등록할 수 있다.
- 등록된 제품 조합이 오늘 피부 상태에 적합한지 점검한다.
- 갑작스러운 피부 문제 발생 시 SOS 형태로 대응 가이드를 제공한다.
- 최근 체크인 기록을 기반으로 주간 피부 리포트를 제공한다.

## 4. 사용자 유형

## 4.1 비로그인 방문자

아직 계정이 없거나 로그인하지 않은 사용자다.

### 가능한 행동

- 랜딩 페이지 보기
- 무료 진단 시작
- 사진 업로드
- 설문 응답
- 무료 결과 확인
- 결과 저장을 위한 로그인 진입

### 제한 사항

- 진단 결과 장기 저장 불가
- 오늘 피부 체크 기록 저장 불가
- 내 제품 관리 불가
- 주간 리포트 확인 불가

## 4.2 로그인 사용자

카카오 또는 구글 로그인으로 인증된 사용자다.

### 가능한 행동

- 내 피부 프로필 확인
- 과거 진단 결과 확인
- 오늘 피부 체크
- 오늘 루틴 추천 확인
- 현재 사용 제품 등록
- 제품 조합 점검
- 피부 SOS 사용
- 주간 피부 리포트 확인
- 유료 리포트 저장 및 재확인

# 7. Usecase 상세

---

## UC-01. 무료 진단 시작

### Actor

비로그인 방문자

### 목적

사용자가 계정 생성 없이 피부 진단을 시작한다.

### Precondition

- 사용자가 서비스 홈에 접속했다.

### Main Flow

1. 사용자가 홈 화면에 접속한다.
2. 사용자가 `무료로 진단 시작하기` 버튼을 클릭한다.
3. 시스템은 사진 업로드 화면으로 이동한다.
4. 사용자는 얼굴 사진을 업로드한다.
5. 사용자는 피부 설문에 응답한다.
6. 시스템은 분석 API를 호출한다.
7. 시스템은 무료 결과 페이지로 이동한다.

### Postcondition

- 무료 결과가 생성된다.
- 세션 또는 임시 저장소에 결과가 보관된다.

### Notes

- 이 단계에서는 로그인을 강제하지 않는다.
- 전환율 저하 방지를 위해 진단 완료 후 로그인 유도를 한다.

---

## UC-02. 진단 결과 저장

### Actor

비로그인 방문자

### 목적

사용자가 생성된 진단 결과를 자신의 계정에 저장한다.

### Precondition

- 사용자가 무료 결과를 확인했다.
- 사용자는 아직 로그인하지 않았다.

### Main Flow

1. 시스템은 결과 페이지에서 `결과 저장하기` CTA를 보여준다.
2. 사용자가 CTA를 클릭한다.
3. 시스템은 카카오/구글 로그인 옵션을 보여준다.
4. 사용자가 소셜 로그인을 완료한다.
5. 시스템은 기존 세션의 진단 결과를 로그인 유저의 `skin_profiles`에 저장한다.
6. 시스템은 `/my` 페이지로 이동한다.

### Implementation Note

OAuth 로그인 과정에서는 페이지 이동과 리로드가 발생할 수 있으므로, 로그인 완료 후 저장할 진단 결과를 복구할 수 있어야 한다.

우선순위:

```txt
1. 로그인 전 freeResult / surveySnapshot / faceLab 요약을 sessionStorage에 유지한다.
2. 가능하면 temporary report id 또는 기존 report session id를 함께 저장한다.
3. OAuth callback 이후 /result 또는 /api/my/save-report에서 저장 가능한 결과를 복구한다.
4. 저장 가능한 결과가 없으면 새 진단을 안내한다.
```

주의:

```txt
로그인 후 결과 데이터가 유실되면 안 된다.
결과 저장 CTA는 단순 로그인 버튼이 아니라, 로그인 후 저장할 데이터를 복구할 수 있는 흐름과 함께 설계한다.
```

### Postcondition

- 사용자 계정이 생성되거나 기존 계정으로 로그인된다.
- 진단 결과가 사용자 프로필에 연결된다.
- 사용자는 로그인 후 홈에서 결과를 다시 볼 수 있다.

### Exception Flow

#### E1. 로그인 실패

- 시스템은 오류 메시지를 보여준다.
- 사용자는 다시 로그인할 수 있다.

#### E2. 저장할 결과 없음

- 시스템은 사용자에게 새 진단을 시작하도록 안내한다.

## UC-03. 로그인 후 홈 확인

### Actor

로그인 사용자

### 목적

사용자가 자신의 피부 상태와 오늘의 루틴을 빠르게 확인한다.

### Precondition

- 사용자가 로그인되어 있다.

### Empty State

로그인 사용자가 아직 저장된 `skin_profile`이 없을 수 있다.

이 경우 `/my`는 오류 화면이 아니라 아래 상태를 보여준다.

```txt
아직 저장된 피부 프로필이 없습니다.
먼저 무료 진단을 진행해 주세요.
```

CTA:

```txt
무료 진단 시작하기
```

이 상태에서는 `오늘 피부 체크하기`를 바로 실행하지 않는다. 체크인은 기준이 되는 `skin_profile`이 있을 때만 생성한다.

### Main Flow

1. 사용자가 `/my`에 접속한다.
2. 시스템은 사용자의 최신 `skin_profile`을 조회한다.
3. 시스템은 오늘의 `daily_checkin` 존재 여부를 확인한다.
4. 오늘 체크인이 있으면 해당 결과 기반으로 홈을 구성한다.
5. 오늘 체크인이 없으면 `오늘 피부 체크하기`를 우선 노출한다.
6. 시스템은 최근 진단 요약, 오늘 루틴, SOS 버튼을 보여준다.

### Postcondition

- 사용자는 오늘 필요한 루틴 액션을 확인한다.

---

## UC-04. 오늘 피부 체크

### Actor

로그인 사용자

### 목적

사용자가 오늘의 피부 상태를 기록하고, 그에 맞는 루틴 조정 결과를 받는다.

### Precondition

- 사용자가 로그인되어 있다.
- 사용자의 `skin_profile`이 존재한다.

### Main Flow

1. 사용자가 `/my/check-in`으로 이동한다.
2. 시스템은 오늘 피부 체크 질문을 보여준다.
3. 사용자는 아래 항목을 입력한다.
   - 당김
   - 유분
   - 붉은기
   - 트러블
   - 자극감
   - 화장 예정 여부
   - 야외 활동 여부
   - 메모
4. 사용자가 제출한다.
5. 시스템은 `daily_checkins`에 기록을 저장한다.
6. 시스템은 `skin_profile + daily_checkin` 기반으로 오늘 루틴을 생성한다.
7. 시스템은 `routine_logs`에 추천 루틴을 저장한다.
8. 시스템은 `/my` 또는 결과 화면에 오늘 루틴 카드를 보여준다.

### Exception Flow

#### E1. skin_profile 없음

- 시스템은 체크인 폼을 보여주지 않는다.
- 사용자를 무료 진단으로 유도한다.
- CTA는 `무료 진단 시작하기`로 표시한다.

#### E2. 오늘 이미 checkin 존재

- 새 row를 생성하지 않는다.
- 기존 `daily_checkin`을 update/upsert한다.
- 연결된 `routine_log`도 새 체크인 값 기준으로 update/upsert한다.

### Postcondition

- 오늘 체크인 기록이 저장된다.
- 오늘 루틴 추천이 생성된다.

### Notes

- MVP에서는 5문항 중심으로 시작한다.
- 하루 1개의 체크인을 기본으로 한다.
- 같은 날짜에 다시 제출하면 기존 체크인을 갱신한다.
- 이후 날씨, 자외선, 생리주기, 수면, 스트레스 등으로 확장 가능하다.

# 10. 핵심 정책

## 10.1 로그인 강제 금지

첫 진단 전에는 로그인을 강제하지 않는다.

```txt
진단 먼저
→ 결과 확인
→ 저장하려면 로그인
```

---

## 10.2 재방문 홈은 제품 판매보다 루틴 점검 중심

로그인 후 홈의 중심은 제품 추천이 아니라 오늘의 피부 상태와 루틴이다.

```txt
오늘 상태
오늘 할 것
오늘 피할 것
내 제품 점검
SOS
```

---

## 10.3 제품 추천은 상황 기반으로 노출

제품 추천은 항상 아래 조건 중 하나가 있을 때만 강하게 노출한다.

```txt
현재 루틴에 빈 단계가 있음
현재 제품이 오늘 상태와 맞지 않음
피부 SOS 상황이 발생함
사용자가 대체 제품을 요청함
유료 리포트에서 예산별 대체안을 확인함
```

---

## 10.4 저장 데이터 우선순위

사용자 재방문을 위해 반드시 저장해야 하는 데이터는 다음 순서다.

```txt
1. skin_profile
2. daily_checkin
3. routine_log
4. user_products
5. sos_log
6. weekly_report
```

---

## 10.5 기존 결과 저장 구조와 충돌 방지

현재 서비스에는 무료 결과, 유료 결과, 공유 결과, premium report 저장 흐름이 이미 존재한다.

새로운 재방문 구조를 만들 때 기존 구조를 무리하게 갈아엎지 않는다.

권장 방향:

```txt
기존 result / full-report flow 유지
→ 로그인 저장 기능 추가
→ skin_profiles에 핵심 결과 복사
→ premium report는 별도 저장 후 user_id 연결
```

---

## 10.6 OAuth 이후 결과 유실 방지

결과 저장은 OAuth 로그인과 연결되므로, 로그인 전 결과 데이터를 복구 가능한 위치에 보관해야 한다.

```txt
sessionStorage freeResult
temporary report id
premium_report_sessions sid
saved report pending state
```

중 하나 이상을 사용해 로그인 후 저장할 결과를 찾을 수 있어야 한다.

---

## 10.7 Phase 1 구현 범위 고정

Phase 1은 아래까지만 구현한다.

```txt
로그인 기반 결과 저장
/my 대시보드
오늘 피부 체크
오늘 루틴 카드
```

Phase 1에서 아래 기능은 구현하지 않는다.

```txt
내 제품 등록
제품 조합 점검
피부 SOS
주간 리포트
알림
캘린더
```

# 11. Codex 구현 지시 요약

Codex는 이 Usecase 기준으로 다음 작업을 진행한다.

```txt
1. 로그인 후 사용자 홈 `/my`를 추가한다.
2. 기존 `/`는 비로그인 랜딩과 로그인 사용자 분기를 처리한다.
3. 진단 결과 저장 기능을 추가한다.
4. 로그인 사용자는 진단 결과를 `skin_profiles`에 저장할 수 있어야 한다.
5. `/my/check-in`에서 오늘 피부 체크를 생성한다.
6. 체크인 결과 기반으로 오늘 루틴 카드를 생성한다.
7. Phase 1에서는 `user_products`, `sos_logs`, `weekly_reports`를 구현하지 않는다. 해당 기능은 Phase 2 이후로 미룬다.
8. 기존 무료 결과, 유료 결과, 공유 기능을 깨지 않는다.
9. 모든 사용자별 데이터는 Supabase Auth `user_id` 기준으로 저장한다.
10. RLS 적용을 전제로 설계한다.
```

# 12. 구현 시 주의사항

## 12.1 기존 진단 전환율 보호

로그인은 진단 전이 아니라 결과 저장 시점에 유도한다.

잘못된 구조:

```txt
홈 접속
→ 로그인 요구
→ 진단 시작
```

권장 구조:

```txt
홈 접속
→ 무료 진단
→ 결과 확인
→ 저장하려면 로그인
```

---

## 12.2 `/my`는 판매 페이지가 아니다

`/my`의 역할은 제품 판매가 아니라 상태 점검이다.

주요 문구 방향:

```txt
오늘은 무엇을 줄여야 하는지

오늘은 어떤 조합을 피해야 하는지
```

## 12.3 체크인은 짧아야 한다

매일 쓰게 하려면 체크인은 10초 안에 끝나야 한다.

MVP 질문 수:

```txt
5개 이하 권장
```

---

## 12.4 AI 호출은 최소화한다

매일 체크인마다 무거운 AI 호출을 하면 비용이 커진다.

권장:

```txt
1차: rule-based 루틴 생성
2차: 필요할 때만 LLM으로 문장 다듬기
3차: 유료/주간 리포트에서 더 깊은 분석
```

---

## 12.5 DB 설계는 확장 가능하게 한다

초기에는 단순한 JSONB 저장을 허용하되, 핵심 검색/집계 필드는 컬럼으로 분리한다.

예:

```txt
dryness_level
oiliness_level
redness_level
breakout_level
irritation_level
makeup_today
outdoor_today
```

상세 루틴 결과는 JSONB로 저장해도 된다.

# 13. 완료 기준

Phase 1 완료 기준은 다음과 같다.

```txt
1. 비로그인 사용자가 기존처럼 진단을 완료할 수 있다.
2. 결과 페이지에서 로그인 후 결과 저장이 가능하다.
3. 로그인 사용자는 `/my`에 접근할 수 있다.
4. `/my`에서 최신 skin_profile 요약을 볼 수 있다.
5. `/my/check-in`에서 오늘 피부 체크를 저장할 수 있다.
6. 체크인 후 오늘 루틴 카드가 생성된다.
7. 새로고침/재접속 후에도 저장된 결과와 체크인이 유지된다.
8. 기존 `/result`, `/result/full-report`, 공유 기능이 깨지지 않는다.
9. 로그인하지 않은 사용자는 `/my`에 접근할 수 없다.
10. 다른 사용자의 `skin_profile`, `daily_checkin`, `routine_log`를 조회할 수 없다.
11. OAuth 로그인 후 저장 대상 결과가 유실되지 않는다.
```
