- 기준 저장소: gycha0109-beep/K_beauty

- 기준 main: b82117394e61cf8fa687768b8f18c88cbb3030f7

- 작업 상태: 설계 초안. 기존 코드·데이터베이스·권한·운영 상품은 변경하지 않음.
- 결정 원칙: **페이스랩은 스킨케어 추천과 독립된 제품 영역이다. 기능 구현에 필요한 공용 기반은 공유하되, 스킨케어 상품 분류·승인·추천 데이터는 페이스랩의 필수 선행조건이 아니다.**

## 1. 상위 제품 정의를 우선한다

프로젝트 제품 정의 「페이스랩 정의 V2 260924.md」의 목적:
- 얼굴의 시각적 특징을 이해한다.
- 사용자 추구미와 현재 상태 사이의 차이를 파악한다.
- 여러 스타일 경로를 비교하고 사용자가 선택한다.
- 헤어, 메이크업, 색, 관리, 안경, 액세서리의 실행안을 제시한다.
- 필요한 경우 실제 제품·색상·서비스·스타일 참고자료로 이어준다.

이는 기존 스킨케어 추천과 다른 문제를 해결한다.
페이스랩 상품 관리 범위를 색조화장품에만 제한하지 않는다. 립, 하이라이터, 베이스, 컬러렌즈뿐 아니라 헤어스타일 참고자료, 안경, 관리 서비스도 다룰 수 있어야 한다.

피부 진단 결과나 스킨케어 선호를 페이스랩에 **자동으로 전파하지 않는다**.
사용자가 명시적으로 허용한 경우 피부 민감도나 회피 성분 같은 제약 정보를 참고하는 연결은 추후 별도로 정의할 수 있다. 이 연결이 없어도 얼굴 분석, 추구미 선택, 스타일 제안 및 독립된 제품 선택은 동작해야 한다.

## 3. 새 구조: 공통 기반은 공유, 업무 의미는 독립

### 3.1 스킨케어 영역 (변경하지 않음)

    스킨케어 설문 / 피부 정보
      → 기존 추천 상품군 및 Product Fact
      → 기존 분류·적합성 평가
      → 스킨케어 제품 추천 / 루틴

- 기존 products / product_fact_subjects / catalog_taxonomy_versions / product_catalog_taxonomy_assignments의 의미·권한·데이터 변경 없음.
- 기존 추천 정확도, 순위, 정식 분류 전환은 별도 업무로 관리.
- 페이스랩을 위해 스킨케어 분류를 변경하거나 신규 임시 승인을 생성하지 않음.

### 3.2 페이스랩 영역 (신규 독립 실행 자료)

    얼굴 분석 + 추구미 + 개인 제약
      → 스타일 변화 제안
      → 복수 실행 경로 중 선택
      → 페이스랩 적용 영역
      → 페이스랩 실행 후보 자료
      → 승인된 상품 옵션 / 스타일 참고자료 / 서비스
      → 얼굴 적용 미리보기 또는 실천 안내

페이스랩 전용 관리 대상은 네 층이다.

1. **실행 대상**: 실제 메이크업 제품군, 컬러렌즈·안경 제품군, 스타일 참고자료, 관리 서비스, 색 조합.
2. **실제 옵션**: 제품에 속하는 색상·호수·크기·종류. 제품군과 옵션은 별도 정체성.
3. **표현 특성**: 색 계열, 언더톤, 명도, 채도, 투명도, 광택, 펄, 질감 및 부위별 적용 특성.
4. **승인 근거**: 적용 가능 영역, 옵션 실재성, 출처, 증거, 참고 이미지 이용 허가, 수정·철회 상태.

헤어스타일이나 서비스처럼 실물 상품이 아닌 후보를 공용 products 테이블에 억지로 삽입하지 않는다.

### 3.3 분류의 책임 구분

- **전사 공용 상품 분류**: 기존 스킨케어 및 범용 상거래 용도. 이번 작업에서 변경하지 않음.
- **페이스랩 실행 유형**: 오직 얼굴 스타일 실행 후보를 고르는 내부 자료 속성. 예: 립 제품, 볼 색조, 컬러렌즈, 안경, 헤어 참고자료.
- **얼굴 적용 영역**: Face Lab Appearance Slot Registry의 현재 19개 직접 적용 영역. 실행 유형과 일대일 등가가 아님.
- **적용 가능성 증거**: 특정 상품 또는 실제 옵션이 해당 영역에 어떤 효과를 낼 수 있는지 별도 승인해야 함.

페이스랩 실행 유형은 기존 상품 분류의 복제나 전사 표준을 주장하지 않는다.
기존 스킨케어 분류 상태나 버전은 독립 페이스랩 후보 승인 여부를 결정하지 않는다.

## 4. 신규 독립 자료 모델 제안 (DB 변경 전 설계)

기존 런타임 계약과 이름이 충돌하지 않도록 **신규 읽기 경계**를 기준으로 먼저 검토한다.
아래 자료명은 개념 이름이며, 실제 테이블·스키마·마이그레이션이 설치됐다는 뜻이 아니다.

| 개념적 자료 | 최소 항목 | 작성·승인 기준 |
| --- | --- | --- |
| 페이스랩 실행 대상 | 고유 ID, 종류(product / style_reference / service / color_palette), 명칭, 관리 상태, 자료 출처 | 검토한 실물 상품 또는 명시적 스타일 자료만 게재 |
| 실제 제품 옵션 | 실행 대상 ID, 자체 옵션 ID, 제품 색상명·호수, 구별 속성, 출시 상태 | 쇼핑몰 문구만으로 임의 ID 발행 불가 |
| 표현 정보 | 옵션 ID, 색상·명도·질감 속성, 각 속성 근거와 검토 버전 | 실제 확인하지 못한 속성은 미상 |
| 영역 적합 근거 | 후보 ID, 스타일 기능, 지원 여부, 심사 방식·버전·증거 참조 | **상품 종류만으로 자동 승인하지 않음** |
| 실행 유형 연결 | 페이스랩 내부 실행 유형, 지원 영역, 검토 버전, 승인·철회 | 상품 개별 적합 증거와 별도 관리 |
| 참고 이미지 | 승인된 자료 ID, 대상 옵션·영역, 역할, 사용 권한, 내용 검증값, 유효 상태 | 웹 주소만으로 허가 추론 금지 |
| 선택적 외부 연결 | 페이스랩 ID ↔ 외부 상거래 또는 스킨케어 상품 ID, 연결 목적·근거·승인 | 없는 경우에도 페이스랩 사용 가능 |

전용 저장소는 공용 DB 내부 별도 보호 구역을 쓰거나 독립 자료 서비스로 둘 수 있다.
기본 제안은 **기존 데이터베이스 안의 페이스랩 전용 보호 저장 영역**이다.
물리적 분리보다 **쓰기 권한·조회 권한·상품 정체성·업무 규칙의 분리**가 핵심이며,
실제 설치 방법은 별도 보안·자료 구조 승인을 받은 후 결정한다.

### 4.1 식별자 규칙

- faceLabItemId: 페이스랩 실행 대상 고유 ID. 기존 스킨케어 products.id와 동일하다고 가정하지 않는다.
- faceLabVariantId: 페이스랩 실물 상품 내 옵션 ID. 제품별로 안정적이어야 한다.
- faceLabCandidateRef: 실행 후보를 참조하는 고유 네임스페이스.
- faceLabSourceRef: 승인 자료의 원 출처 식별자.
- 외부 상품번호와 기존 Product Fact Subject ID는 **선택적 연결 정보**이지 필수 자식 관계가 아니다.

기존 product_variant:<productId>:<variantId> 참조 생성 함수에 다른 의미의 ID를 몰래 대입하지 않는다.
새 자료 모델에 필요한 참조·어댑터 계약을 따로 만든 다음 실제 사용 경로를 함께 수정한다.

### 4.2 출처·승인 상태

신규 자료는 초안 → 심사 대상 → 승인 → 중지/철회의 흐름을 가진다.
개별 속성, 적용 기능, 참고 이미지의 승인 주체·근거·유효 여부를 구분한다.

- 신규 카탈로그 등재 = 미리보기 승인 아님.
- 제품 종류 분류 = 색상 발색 보증 아님.
- 색상 스와치 존재 = 착용·도포 결과 보증 아님.
- 승인된 상품 = 모든 얼굴 적용 영역 지원 아님.
- 예전 승인 자료는 철회·변경되면 재검토하기 전까지 사용 금지.
- 출처 문자열이 올바른 형식이라는 이유만으로 실제 자료 존재와 사용권을 입증했다고 간주하지 않는다.

## 5. 신규 읽기와 실행 경로의 최소 계약

페이스랩 전용 상품 조회는 다음처럼 분리한다.

    사용자가 선택한 페이스랩 대상·옵션·적용 영역
      ↓
    서버의 인증 및 접근 범위 확인
      ↓
    페이스랩 전용 승인 자료 조회
      ↓
    실행 대상/옵션 정체성 검증
      ↓
    적용 기능 증거 + 승인된 표현 특성 검증
      ↓
    승인된 참고 이미지 메타 정보 검증
      ↓
    기존 스타일 합성기 및 이미지 요청 준비
      ↓
    사용자가 명시적으로 실행할 때만 이미지 생성

제안 입력 계약(개념):

    readFaceLabApprovedSelection({
      faceLabItemId,
      faceLabVariantId,   // 상품 옵션이 없으면 생략 가능
      slotKey
    })

상품군이 아닌 스타일 참고자료·서비스에는 무조건적인 faceLabVariantId가 필요하지 않다.
서비스는 안내용 결과까지만 지원할 수도 있으며, 별도 시각 참고자료 승인이 없는 경우 가상 체험 가능으로 표시하지 않는다.

이 함수가 새로 공급하는 후보 구조만 기존의 적용 영역, 기능 근거 검사, 합성기, 이미지 입력 검사로 전달한다.
이전 catalog-product-try-on-read-core.js 경로는 v1 호환성 보존을 위해 당장 삭제하지 않고 안전 차단 상태로 유지한다.
새 경로에서 products·product_fact_subjects·전사 catalog taxonomy를 필수 조회하지 않는다.

### 5.1 독립 선택 성공 조건

다음 모두 만족해야 가상 적용 가능한 후보로 노출할 수 있다.
1. 해당 실행 대상이 활성·승인 상태다.
2. 실물 제품인 경우 실제 옵션이 유효하며 출처 근거가 있다.
3. 해당 얼굴 적용 영역에 대한 기능 지원이 증명돼 있다.
4. 필요한 색·표현 속성이 검증됐거나 해당 적용 방식의 안전한 대체 근거가 있다.
5. 필요한 참고 이미지가 승인돼 있고 파일 무결성·이용 권한을 확인할 수 있다.
6. 해당 사용자에게 조회·사용 권한이 있고 요청된 모델·비용 정책을 만족한다.

승인 자료가 없으면 억지로 보완하지 않는다.
다만 **상품 자료 미준비로 페이스랩의 얼굴 분석·추구미·스타일 경로 전체를 막지는 않는다.**
상품 실행 부분만 '연결된 상품 준비 중'으로 표시할 수 있다.

## 6. 스킨케어와의 선택적 연결

공통 회원 계정, 구독 해금 여부, 안전한 이미지 처리 기반은 공유 가능하다.

선택적 연결 예시:
- 페이스랩 사용자가 피부 민감도 참조를 허락하면, 검증된 피부 제약만 스타일 실행 후보 필터에 제한적으로 반영.
- 페이스랩 색조 상품이 기존 비주얼리 상품과 우연히 겹치는 경우, 양쪽 상품번호를 **심사된 별도 연결표**로 대응.
- 사용자가 스킨케어 추천을 사용한 적이 없어도 페이스랩을 사용할 수 있음.

연결 금지:
- 스킨케어 제품군·루틴 점수 또는 피부 적합성을 얼굴의 스타일 적합성으로 치환.
- 스킨케어 Product Fact formulation key를 색상/호수로 해석.
- 페이스랩 사용자 얼굴 사진·추구미·결과를 스킨케어 추천에 자동 유입.
- 기존 상품 추천용 특권 계정·조회 함수·승인 이력을 페이스랩 권한으로 재사용.
- 스킨케어 카탈로그 분류 정식 승인을 페이스랩 출시 전제 조건으로 설정.

## 7. 기존 결과와 정합성

**유지**
- Face Lab 얼굴 특성 추정·추구미·차이·경로 비교·선택
- 19개 기존 적용 영역·출시 순서·사용자 선택 우선권
- 현재 기능 지원 증거 계약, 실제 색상·옵션 근거 검사
- 선택 영역만 수정하는 얼굴 동일성·수정 범위 규칙
- 참고 이미지 권한·해시·파일 형식·용량·순서 확인
- 여러 후보를 모으는 가상 화장대와 변경 이력
- 무료 검증과 유료 이미지 호출 제한

**의미를 바꿔야 하는 부분 (승인 후 코드 작업)**
- 기존 공용 products.id만 받아들이는 읽기 경로
- 기존 Product Fact Subject 강제 연결과 sourceVariantRefs의 의무 출처
- 기존 catalog-taxonomy-v1 정식 분류 통과를 실행 조건으로 강제하는 검증
- categoryBinding이 기존 분류 버전·term ID만을 참조하는 계약
- 참고 이미지·가상 화장대의 상품 참조 네임스페이스
- 해당 필수 조건을 재현한 기존 단위 테스트의 **독립 경로용 신규 테스트** 추가

**변경하지 않을 영역**
- 기존 스킨케어 추천·상품 분류·제품 신뢰도 관리·기초 루틴
- 기존 상품 SQL 자료, 권한 정책, 데이터베이스 저장값
- 현재 Face Lab 관찰·평가·이미지 생성 서비스의 승인된 품질 기준

## 9. 회귀 검증 및 실패 조건

**통과해야 할 독립 동작:**
- 스킨케어 상품·Subject·Taxonomy DB 없이 페이스랩 실행 후보 계약의 순수 함수 검사 통과.
- 기존 사용자 얼굴 분석·추구미·경로 선택은 상품이 없어도 동작.
- 승인된 페이스랩 옵션과 영역별 기능·근거·색 정보가 연결된다.
- 실제 상품과 스타일 참고자료의 ID가 서로 충돌하지 않는다.
- 같은 상품이 서로 다른 두 적용 영역에 들어갈 수 있고 슬롯 중복은 거부된다.
- 스킨케어와 연결이 필요할 때는 명시적으로 승인한 자료만 한 방향으로 읽는다.

**반드시 막을 사례:**
- 승인 없는 화장품·가짜 호수·근거 없는 색상·잘못된 영역 지원
- 다른 상품의 이미지를 교차 바인딩하거나 불허된 사용권의 이미지 적용
- 철회된 상품·옵션·근거·참고 이미지
- 없는 스킨케어 연결을 자동 생성하거나 스킨케어 분류로 묵시적 대체
- 인증되지 않은 사용자, 허용되지 않은 DB/이미지 권한
- 허가되지 않은 유료 이미지 모델 호출

**이행 안전성:**
- 구형 상품 조회/바인딩을 삭제·변경하기 전 의존 호출부와 기존 검증 목록을 정확히 수집한다.
- 새 독립 경로가 검증될 때까지 v1 경로를 안전하게 차단하고 기존 추천 서비스는 그대로 유지한다.
- 기존 단위 검증 기준을 낮추지 않고 독립 경로의 새 회귀 검증을 추가한다.
- 실패 원인을 숨기기 위해 임의 샘플 제품을 운영에 넣지 않는다.
