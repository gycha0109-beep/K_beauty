# [Face Lab / Skin] S1→S2 사진 축별 관찰/0점 분리 설계안 v1 — 2026-10-15

> **상태: 설계안 / 구현·운영 활성화 미승인.** 기준 `main@1a82cf9961f4fbba30d1d59f1ec2de1a3c6dd7e2`. 연결 로드맵 #1307, 전수 감사 #1308, 사진 실패 상태 보수 #1309, 설문/사진 비교 보수 #1316. Skin Track만 담당한다. Style Track 및 공통 카메라·단일 Vision 호출 소유권을 침범하지 않는다.

## 1. 해결해야 할 실제 문제

현행 공유 Vision 요청은 `skin.signals`의 8개 축에 **각각 0–5 정수**를 강제하고, 사진이 부적격이거나 개별 축 근거가 없을 때도 **0을 쓰라**고 지시한다(`lib/vision-observation-contract.js`).

`lib/vision-observation-normalizer.js`는 누락되거나 변환할 수 없는 값도 `0`으로 바꾼다. `lib/skin-observation-projector.js`는 숫자와 최대 3개의 관찰 단서를 결과에 전달한다. `lib/skin-match-decision-engine-core.js`의 `applyPhotoWeights`는 사진 전체 `skinAnalysisEligible`만 확인한 뒤, 각 축의 숫자에 4(자외선은 3)를 곱해 사진 점수를 더한다. **개별 축을 관찰했는지와 그 관찰의 신뢰도는 점수 계산에 사용하지 않는다.** 관찰 목록은 최대 4개이며 전체 8축의 '안 보임' 여부를 대신할 수 없다.

따라서 지금 0에는 다음이 섞인다.

1. 해당 단서를 평가하기에 사진이 충분히 선명했고 **그 단서가 눈에 띄지 않았음**.
2. 해당 부위가 가려졌거나 조명·화장·필터 때문에 **판단할 수 없음**.
3. 해당 축에 대한 관찰 또는 Provider 필드 자체가 **없음**.
4. Provider 실패, 입력 부적격 또는 사진 미제공으로 **분석 자체가 없음**.

반대로 숫자 4~5가 있어도 같은 축에 대한 믿을 만한 직접 관찰은 없는 경우가 가능하다. 단지 숫자 양수라는 이유만으로 사진 점수를 정당화할 수 없다.

**설계 목표:** 각 축의 관찰 가능 여부·직접 근거·신뢰도·값을 분리 보존하고, **확인하지 못한 것=정상**, **확인하지 못한 것=설문과 반대**, **높은 숫자=높은 신뢰도** 등의 도약을 금지한다.

## 2. 항목별 새 관찰 표현

### 2.1 사진 단서에 해당하는 7축

`oiliness`(표면 광택), `dehydration`(건조해 보이는 결/각질), `acne`(국소 spots의 외관), `uneven_tone`(사진상 톤 차이), `pores`(모공 가시성), `redness`(붉어 보이는 부분), `barrier`(표면 스트레스/거칠기 외관)만 사진 축으로 사용한다.

`uv`는 현재 Vision 관찰 목록에 직접 관찰 단서가 없으므로 **사진 상태 검증에서는 제외**한다. 단, **기존 자외선 관련 설문·환경·자외선 차단제 보호 정책은 유지**한다. 장기적으로 사진의 UV 가산점을 제외하는 것은 제품 추천 변경이므로 별도 승인 전 활성화하지 않는다.

### 2.2 상태의 뜻

| 상태 | 점수 | 뜻 | 사진 점수 반영 후보 |
| --- | --- | --- | --- |
| `present` | 1~5 | 해당 축과 맞는 눈에 보이는 단서를 확인함 | 같은 축 근거와 신뢰도까지 검증된 경우에만 **검토 가능** |
| `not_seen` | 0 | 해당 부위를 판단할 수 있었으나 **그 시각적 단서가 보이지 않음** | 0점, 감점 없음. 피부 상태가 정상이라고 해석 금지 |
| `unassessable` | `null` | 이 사진 조건에서는 그 축을 볼 수 없음 | 반영 금지, 관찰 보류 |
| `unknown` | `null` | 값/필드가 없거나, 결과의 신뢰도를 해석할 수 없음 | 반영 금지, 관찰 보류 |

**주의:** `not_seen`은 '실제 피부에 문제가 없다'거나 '이 질환이 없다'는 뜻이 아니다. '이 사진에서 식별 가능한 외관 단서가 눈에 띄지 않는다'는 제한된 주장이다. `present` 역시 의료적 진단이 아니다.

각 축은 공통 필드 `state`, `value`, `confidence`, `cue`, `area`, `reason`을 갖는다.
- `confidence`: `low | medium | high | unknown`. 모델이 적은 수준은 **확률이나 검증된 정확도 수치로 취급하지 않는다**.
- `cue`: 기존 `VISION_SKIN_CUES`의 축에 대응하는 시각적 단서. `uncertain`은 확정 관찰에 사용할 수 없다.
- `area`: 기존 `VISION_SKIN_AREAS`에 한정.
- `reason`: `none | blur | occlusion | lighting | makeup | filter | low_resolution | unsupported | missing | provider_failure` 등 닫힌 목록을 별도 계약으로 관리. 사유를 임의 추론하지 않으며, `unknown`에는 필요에 따라 `missing` 또는 `unsupported`를 유지한다.

**일관성 검증:**
- `present`에서만 `value`는 1–5; 실제 관찰과 연결된 `cue/area`가 있어야 한다.
- `not_seen`은 사진의 해당 부위를 판별할 수 있었던 근거와 중간 이상 신뢰도가 있을 때만 `value=0`. 숫자 0만으로 자동 생성 **금지**. 관찰 신뢰도가 낮으면 `unassessable` 또는 `unknown`으로 보류한다.
- `unassessable/unknown`은 `value=null`; 결과 점수 0으로 치환 **금지**.
- `present`라도 낮은 confidence면 보수적으로 **점수 반영 보류**; 없는 근거를 숫자로 보완하지 않는다.
- 하나의 축에서 중복·상충 관찰이 있으면 임의로 높은 점수를 택하지 않고 보류·검토로 보낸다.
- 다른 축 관찰 또는 사진 전체 자격 통과는 해당 축의 근거가 아니다.

## 3. 현재 구조에 연결하는 설계

### A. 사진에서 정보를 받아오는 단계

- 기존 **Skin + Style 공용 사진 요청 1회**를 유지한다. 사진을 한 번 더 AI에 보내거나 원본/얼굴 특징을 추가 저장하지 않는다.
- 관찰 응답을 `vision-observation-v2`로 **명시적으로 버전 구분**하는 방식을 우선 채택한다. v1에서 '지원하지 못한 축=0' 규칙을 몰래 바꾸지 않는다.
- 새 v2 `skin.axisEvidence`는 위 7축에 대해 **각각 명시적인 상태**를 요구한다. 요약용 관찰 문장은 최대 4개여도, 각 축의 확인/보류 상태는 모두 기록한다. 4개 문장 누락을 '정상'으로 해석하지 않는다.
- 비교 검증기에는 기존 숫자 `skin.signals`와 새 축별 상태를 **한 응답에서 함께 받을 수 있는 과도기 계약**을 둔다. 기존 숫자 8개는 그 자체로 근거가 되지 않으며, 상태와 숫자가 충돌하면 **새 사진 점수는 보류**한다. 과도기 숫자까지 포함할지, 정규화 시 파생시킬지는 실제 답변 길이·안정성 검증에서 최종 선택한다.
- 공용 Face/Style 응답 구조, 사진 자격 판정 및 횟수는 건드리지 않는다. 새 피부 응답이 불완전할 때 **피부 사진 근거만 실패 처리**하는 경로와 공용 응답 실패 정책은 별도 영향 검토가 필요하다.

### B. 데이터를 정리하는 단계

- `lib/vision-observation-normalizer.js`는 v1 데이터를 v2로 추정 승격하지 않는다. **과거 v1의 0은 영구적으로 '구별 불가'**다.
- v2는 숫자 0을 만들어 채우지 않고, 항목별 `state/value/confidence`를 보존한다. 잘못된 수치, 지원하지 않는 열거값, 단서와 축의 불일치는 **불확실/보류**로 분류한다.
- 한 축에 문제가 있어도 가능한 다른 축과 공용 Face/Style 분석까지 전부 '정상' 또는 전부 '실패'로 왜곡하지 않는다.
- 기록에 사진 실패가 명시돼 있으면 단서 객체 존재 여부와 무관하게 실패를 우선한다(#1309와 같은 원칙).

### C. 피부 판단에 반영하는 단계

**처음에는 실제 추천 계산식을 바꾸지 않는다.** 동일한 사진 요청의 결과로 기존 계산값과 새 규칙의 가상 계산값을 **내부에서만 나란히 비교**한다.

가상 계산의 기본 원칙:

```text
사진 전체가 분석 가능한가?
  아니요 → 사진 가산점 전부 0, 설문/환경 판단 유지
  예 →
    해당 피부 항목을 시각적으로 관찰했는가?
      아니요 / 모름 → 그 항목의 사진 점수 반영하지 않음
      관찰했지만 단서가 안 보임 → 사진 가산점 0, 감점 없음
      단서가 보임 →
        같은 항목의 시각적 근거가 있고 신뢰도 충분?
          아니요 → 사진 점수 반영하지 않음
          예 → 기존 항목별 가산 공식의 입력 후보로 인정
```

- **임시 검증 기준**은 `medium/high`만 가산 후보, `low`는 반영 보류. 실제 적용 기준은 독립 사람 평가 후 확정한다. 숫자 가중치를 'low=0.3, high=1.0' 같은 임의 계수로 바꾸지 않는다.
- 인정된 양성 단서에만 **기존 곱셈 방식**(사진 1~5 × 4) 후보를 사용한다. 설문/환경 점수, 고민 우선순위의 동점 우선 규칙, 제품 필터, 기존 보호 유지 규칙은 바꾸지 않는다.
- 근거 없는 사진 점수는 다른 축이나 설문에 비율로 재분배하지 않는다.
- 자외선 관련 사진 점수는 새 관찰 기준에서 승인 전 **산출 불가**이며, 별도 비교/영향 보고 없이 즉시 제거하지 않는다.
- 기존 `applyPhotoWeights`는 새 판단 엔진으로 복제하지 않고, 승인된 좁은 수정에서만 변경한다.

### D. 저장 결과와 화면

- 새 분석은 사진의 축별 관찰/보류 상태를 **구조화된 보조 정보**로 표시할 수 있다. 예: '붉은기는 사진상 확인됨', '건조해 보이는 결은 사진만으로 판단 어려움'.
- '판단 어려움'을 '해당 고민이 없음', '피부 정상', '사용 가능'으로 변환하지 않는다. 설문 우선 또는 재촬영 안내를 제공한다.
- 기존 저장 리포트는 **그때의 점수·추천·행동·기록 버전을 그대로 읽는다**. 과거 0점을 근거 있는 '없음'으로 소급 변환하지 않는다.
- 새 기록 형식의 저장·재진입, 사용자 동의/보유기간, 개인정보·계정 접근 규칙 변경은 **저장 권한 담당자의 독립 승인** 이후. 기존 v4의 기록 확인값/hash/revision을 조용히 덮어쓰지 않는다.
- Premium 네 개의 Skin 섹터에는 동일한 상태 의미를 사용하되, Style Track의 얼굴 형태/퍼스널컬러 판단과 합치지 않는다.

| 같은 사람 사진에서 다른 조명·화장·기기 | 축별 차이를 피부 변화로 오해 가능 | 비교 불가/제한 표기, 변화·호전 단정 금지 |
| UV 숫자 4, 직접 관찰 단서 없음 | 사진 12점 | 새 사진 규칙에서는 인정 불가 후보, 제품 추천 영향 별도 심사 |
| 과거 v1 저장 리포트에 0점 | 0의 이유 복원 불가능 | 기존 점수·추천 보존, 사진 근거 세분화는 `unknown` |
| 같은 사진, 새 규칙과 기존 추천이 다름 | 조용한 추천 변동 우려 | 사용자 공개 전 항목별 차이·원인·안전성 검수 |

## 5. 실제 구현 순서와 허용 범위

1. **설계·검사만 추가:** 위 4상태·값/신뢰도·이유 목록, 축별 모순·중복/누락 부정 사례. 기존 운용 코드와 응답 불변.
2. **새 피부 관찰 계약:** 단일 Vision 요청/공용 Face 계약 유지 조건을 확인하고, 통제된 환경에서 응답 형식·응답 길이·비용·실패율 검증. 개인정보 없는 합성 자료부터 시작.
3. **두 계산 방식 나란히 비교:** 기존 제품 점수/추천은 그대로 사용자에게 전달한다. **같은 사진 요청**에서 생성된 1회 관찰 정보로만 새 방식 결과를 계산, 실서비스 사용자에게 조용히 적용하지 않는다. 단일 요청에서 v1/v2 동시 점수 비교가 가능한 실제 응답 계약을 먼저 검증한다.
4. **독립 사진 검증:** 동의된 비공개 사진에서 축별 실제 가시 단서, 오탐/미탐, 보류율, 다른 조명/기기, 평가자 간 차이를 측정한다. 임의로 정한 신뢰도 기준을 사람 평가로 보정한다.
5. **추천 차이 점검:** 기존 고정 평가(164개 제품 × 12개 조건), 사진 없는 경우/실패/사진 상태 미확인 케이스, 주요 추천·우선순위·주의 행동 변동을 전량 점검한다. 차이가 나타나면 고쳐서 숨기지 않고 원인/근거/사용자 영향 및 담당자 승인까지 기록한다.
6. **저장·화면 호환성 점검:** v1 재진입·사진 미제공·실패·Unknown/HOLD·기존 Premium 정책을 보존한다. 저장 형태가 바뀌면 독립 개인정보/DB/RLS 승인 후에만 적용.
7. **점진적 운영 활성화:** 위 근거가 충족된 뒤에만 별도 승인으로 Skin 가산점 반영을 전환한다. 문제가 생기면 구방식으로 복귀할 수 있어야 한다. 단순히 과거 추천을 다시 계산하거나 사용자의 저장 기록을 일괄 수정하지 않는다.

**진행 허용:** 단계 1의 문서·순수 합성 검사, 기존 결과를 건드리지 않는 관찰 검토.
**별도 승인 필요:** 공유 Vision 요청 계약/실제 사진 비용, 추천 점수 변경, 저장/계정·개인정보 정책, 운영 활성화 및 배포.

## 6. 완료 판정 — 수치와 안전성

자동 검사로 확인할 절대 조건:
- 근거 없음/관찰 불가/누락/Provider 실패 상태에서 **사진 가산점 발생 0건**(새 규칙 기준).
- 각 축의 `0`과 `null`은 정규화→설문 비교→표시까지 의미가 **서로 합쳐지지 않을 것**.
- `low` 관찰을 `medium/high`처럼 처리하는 사례 0건, 축 불일치를 억지로 다른 축에 귀속한 사례 0건.
- 사진 미제공 경로의 설문·환경 결과 **기존과 동일**; 기존 기록 자동 재계산 0건; 공유 Vision 호출 횟수 증가 0건.
- 사람이 검수한 실제 사진이 없으면 정확도/사용자 안전성을 '통과'로 표시하지 않을 것.

**별도 실제 사진 평가로 결정할 조건:** 축별 오탐·미탐·보류율, 촬영 조건별 격차, 의견 일치도와 판단 실효성의 허용 기준은 **실측과 독립 검수 후 확정**한다. 현재 근거 없이 특정 '정확도 90%' 등의 수치를 지어내지 않는다.

**릴리스:** 제품 정확도와 출시 준비는 별개의 판단. 보안 #1208은 독립 차단이며 임의 예외 연장/무시 금지.

## 7. 권장 분할 작업(한 번에 출시 변경 금지)

- **작업 A — 순수 계약/검사:** 피부 축별 상태 정의, 합성 시험, 오류 복원 불가 규칙 (추천/운영 변화 0).
- **작업 B — 단일 Vision 응답 확장:** 정확한 스키마 버전/모델 출력 한계/Style 호환 검증 (적격한 권한의 리뷰 필요).
- **작업 C — 비노출 비교 계산:** 가상 사진 점수·추천 차이 기록, 기존 사용자 결과 불변.
