## 2. 업무와 저장의 분리

```text
[등록/검수 담당자] ──기존 관리자 로그인+별도 페이스랩 권한 확인──┐
                                                              ▼
                 페이스랩 비공개 운영 자료(초안/근거/버전/심사 이력)
                                     │ 검수, 승인, 공개
                                     ▼
               현재 공개본 식별자 + 현재 철회 상태(서버 기준)
                                     │ 제한 조회
[최종 이용자] ──로그인/기능 사용 권한──> 전용 서버 조회 경계
                                     │ 승인된 최소 정보
                                     ▼
            기존 Face Lab 상품 검증 → 무료 합성 미리보기 지시서
                                     │
                          실제 이미지 호출은 별도 승인
```

- 상품 계층: `product`, `style_reference`, `service`, `color_palette`. 서비스와 색 조합은 기본 **안내용**.
- 페이스랩 상품 ID와 실제 옵션 ID는 기존 스킨케어 상품 번호에서 추론하거나 재사용하지 않는다.
- 헤어/안경/액세서리/메이크업 중 Face Lab이 실제 지원하는 실행 영역만 참조한다.

### 3.1 물리적 분리 추천

- 비공개 업무 스키마(가칭 `face_lab_catalog_private`)를 **Data API 비공개 목록**에 유지하는 방식 우선 검토.
- 원본 상품 정보, 미공개 후보, 증거/권리 증빙, 심사 사건 기록을 브라우저에 직접 노출하지 않음.
- 공개 후보로 필요한 최소 필드(상품명, 옵션, 적용 부위, 상품별 기능 상태)만 서버가 제한해 제공.
- 목록용 표시 자료는 공개본 읽기 전용 투영을 통해 제공할 수 있지만, **그 투영만으로 가상 이미지 실행 권한이 생겨서는 안 된다**.
- 상세 내용은 고정된 내용 버전과 지문을 공유하고, 새 버전을 공개하지 않으면 이전 승인 상태가 다른 자료 내용에 붙지 않게 한다.
- 내부 저장 방법(정규화 테이블/버전 불변 객체)은 후속 SQL 리뷰에서 선택. 현재 자료와 마이그레이션 이름을 예고 없이 변경하지 않는다.

### 3.2 데이터 일관성 제약(구현 전 명세)

- 키 재사용 금지: 삭제한 상품/옵션 ID를 새 실물에 재할당하지 않는다.
- 동일 상품/옵션을 두 후보로 자동 합치지 않는다. 중복 의심은 **심사 대기**로 표기.
- `item_id`나 `variant_id`와 `candidate_ref`의 결속은 서버가 계산해 확인.
- 이미지 객체는 **덮어쓰기 금지**. 수정 시 다른 파일 키·내용 지문·승인 이력을 새로 작성.
- 동일 공개본의 모든 구성요소는 검증된 내용 지문과 승인된 개별 버전을 포함해야 한다.
- 승인 이벤트의 원인, 대상, 사용자, 권한, 기대 버전, 결과, 시각을 기록한다. 조작 가능한 문자열을 실제 사용자·권한 증거로 취급하지 않는다.
- 개인정보(얼굴 사진·피부 정보·추구미·생성 결과)는 상품 운영 저장소에 넣지 않는다.

## 4. 공개 상태와 철회 상태: 서로 다른 책임

**공개 여부의 신뢰 근거**는 두 요소의 교집합으로 판단한다.

1. **변경 불가능한 공개본**: 해당 상품·옵션·색상·기능·참고 이미지의 승인 사건, 내용 버전, 해시가 고정된 구성.
2. **현재 사용 가능성 표시**: 상품·옵션·이미지별 현재 철회/일시중지 상태와 `revocation_epoch`.

`approved`/심사 이력만 있다고 쓰지 않고, **최신 현재 상태를 반드시 재확인**한다.

### 4.1 원자적 심사 변경

한 번의 관리자 승인/철회 처리는 논리적으로 같은 거래 안에서 수행:

1. 서버가 실제 사용자 인증 후 **해당 페이스랩 전용 권한**을 확인.
2. 입력 ID/작업 종류/기대 개정번호/사유/요청 중복방지 번호를 검증.
3. DB 거래에서 해당 대상의 현재 상태/개정번호를 잠그거나 조건부 비교-변경으로 보호.
4. 업무 상태 전이가 가능한지 검사하고, 필수 원문 증거/사용권 상태를 DB에서 재조회.
5. 변경 불가능한 감사 사건과 현재 상태 변경, 공개본 포인터/철회 세대 업데이트를 **함께 확정**.
6. 거래가 실패하면 이력과 공개 상태를 함께 취소. 부분 성공 금지.
7. 중복 요청 번호 재전송 시 동일 결과를 안전하게 재현하고 이중 공개/철회를 막음.

**중요:** 지금의 `transitionFaceLabCatalogReview`는 오프라인 객체 전이만 계산하며 DB 거래·실제 관리자 검증은 수행하지 않는다. DB 내부 거래 원자성은 후속 승인된 구현에서만 보장될 수 있다.

### 4.2 철회와 경쟁 상황

- 철회 요청이 성공으로 반환된 후 시작되는 **새 조회/새 적용/재생성**은 반드시 철회 상태를 확인해 거부.
- 선행 조회와 철회가 동시에 발생하면, 실행 직전 현재 상태/철회 세대를 다시 검사하여 오래된 승인본의 사용을 차단한다.
- 이미지 생성과 같은 장기 실행이 **이미 시작된 뒤** 철회되는 상황까지 완전한 중단을 약속하지 않는다. 향후 실행 중 취소/비용 처리·결과 노출 금지 정책이 별도 필요.
- 공개본의 목록 캐시는 허용하더라도 **실행 가능 판단을 캐시만으로 결정하지 않는다**.
- 구버전의 승인 이력이 남아도 `revocation_epoch`가 달라지면 재승인 전 사용 불가.
- 서버/DB 장애·거래 실패·철회 데이터 미조회·시계 또는 만료 판단 불가 → 안전 거부.

## 5. 관리자 권한: 기존 회원 체계의 **최소 확장**

### 5.1 기존 체계에서 확인된 사실

현재 코드에 존재:
- `admin_memberships`를 읽는 `resolveCurrentAdminAccess()` (로그인 및 비익명 계정 검사 포함)
- 역할 `admin_viewer`, `admin_operator`, `admin_privacy`, `admin_owner`
- `admin.products.review` 등 일부 상품 관련 권한
- 변경 요청에 대한 `isAllowedAdminMutationRequest()`
- 감사 로그 `admin_audit_logs`

**이것은 페이스랩의 등록/검수/승인을 현재 관리자가 할 수 있다는 증거가 아니다.**
`admin.products.review`는 기존 상품 업무 권한이며 페이스랩의 `approve/publish/revoke` 자동 승인 근거로 재사용하지 않는다.

### 5.2 제안하는 세분 권한

| 신규 개념 권한 | 허용 | 초기 승인 규칙 권고 |
| --- | --- | --- |
| `face_lab.catalog.read` | 전용 상품 관리 자료 조회 | 지정된 관리자 |
| `face_lab.catalog.create` | 등록·수정·심사 요청 | 지정된 편집 관리자 |
| `face_lab.catalog.review` | 증거 검토·반려·승인 | 별도 심사 권한 |
| `face_lab.catalog.publish` | 공개본 포인터 갱신 | 명시적 공개 권한 |
| `face_lab.catalog.revoke` | 중지/철회 | 긴급 대응 권한, 감사 필수 |

- 위 문자열은 **설계 후보**이고 현재 `ADMIN_CAPABILITIES`에 없다. `admin_operator`에 일괄 자동 부여하지 않는다.
- 현실적 1인 운영을 지원하되, `create`와 `review`는 서로 다른 관리자 **행위**로 기록하고 자기 승인 허용 여부는 출시 전에 명시적으로 결정.
- 권한 확인은 브라우저 주장/수정 가능한 사용자 메타데이터가 아니라, 서버가 검증한 로그인 사용자와 DB가 관리하는 활성 회원/권한에서 수행한다.
- `admin_owner`라도 자료 출처·실제 이미지 사용권/버전 검사를 생략하지 않는다.
- 관리자 쓰기는 원점 검사, 요청 위조 방지, 작업별 중복방지, 규모 제한, 오류 기록 비식별화를 적용.
- `admin_audit_logs`는 관리자 접근/행위 감사의 **보조 기록**으로 재사용 가능하나, Face Lab 공개본의 자체 버전·철회 판단에 필요한 **업무 사건 기록**을 대체하지 않는다.

## 6. 일반 사용자: 새 전용 조회 경계

개념상 서버 서비스명: `readPublishedFaceLabSelection` (아직 구현하지 않음).

**받아야 하는 최소 입력:**
- `faceLabItemId`
- `faceLabVariantId?` (실물 상품만 필수)
- `slotKey`

**사용자가 절대 제출하지 않는 값:**
- 승인/철회 상태, 심사 사건/심사자 역할, 원문 증거, `sourceDigest`, `storageKey`, 이미지 파일, 출력할 내부 공개본 객체.

서버 절차(서로 다른 API 호출로 수행해도 보안 규칙 일치 필요):

1. 기존 사용자 세션/접근 토큰을 서버에서 실제 검증. 익명/구독/기능 해금 정책은 현행 Face Lab 권한 계약을 확인해 적용.
2. ID/옵션/부위의 입력 형식과 크기/횟수 제한.
3. **페이스랩만의 비공개 조회 권한**을 가진 서버 경계에서 현재 공개본을 가져옴. 스킨케어 추천 자료 조회 금지.
4. 같은 시점의 상품/옵션/색상/적용 기능/참고 이미지 버전과 심사 상태, 현재 철회 세대를 함께 읽음. 가능한 경우 **단일 원자적 읽기 거래**에서 구성. 여러 요청으로 분리될 경우 개정번호 재조회 불일치를 거부.
5. 해당 사용자에게 선택한 기능 접근이 허가돼 있는지 검증. 서버 자료만 `validateFaceLabIndependentExecutionCandidate` → `composeFaceLabReviewedLookDryRun`으로 전달.
6. 파일 사용권/용도/만료·저장 객체 소속과 메타 정보 검사. 이는 **실제 원본 해시 확인을 대체하지 않음**.
7. 사용자에게 표시할 최소 정보/사용 불가 사유만 반환. 내부 증거·감사 이력·비공개 객체 경로/실제 권한 토큰은 절대 응답하지 않음.
8. **가상 이미지 생성은 열지 않음.** 향후 별도 승인된 실행 경로에 대해서는 실행 직전 최신 철회 세대와 **파일 실제 바이트 해시**를 다시 확인해야 함.

### 6.1 제안하는 결과 상태

- `available`: 서버가 신뢰할 수 있는 현재 공개본 검증 완료. **상품 선택 가능성이지 유료 생성 허가가 아님**.
- `guidance_only`: 비상품 안내용. 가상 체험 제공 금지.
- `not_ready`: 심사 미완료/증거 부족/사용권 만료/철회/자료 오류. 안전하게 사용 불가.
- `unavailable`: 인증/권한/저장소/서버 검증 실패. 사용 불가.

**오류 의미:** 비공개 상품의 존재 여부/심사 내용/관리자 정보를 유추할 수 없도록 대외 사유를 축약한다. 상세 원인은 민감 정보 없는 서버 로그만 사용.

현재 오프라인 합성기의 `previewSpec.status: ready`와 `renderReady: false`를 혼동하지 않는다. 서버 조회 성공만으로 `providerRequest`를 생성하지 않는다.

## 7. 보안 구현 대안: 무엇을 우선 추천하는가

**우선 권고:** DB의 비공개 스키마/테이블 + 엄격하게 제한한 **서버 전용 조회·관리 경계**.

세부 DB 접속 방식은 현재 배포 서비스/호스팅 구성과 운영 자격증명 관리 능력을 확인한 뒤 고른다.

| 방안 | 이점 | 단점·선행 확인 |
| --- | --- | --- |
| A. 전용 최소권한 DB 사용자·서버 거래 | 특정 테이블 SELECT/관리 전이 권한만 부여하고 거래 일관성 구현이 명확 | 새로운 보안 자격증명/배포 설정/연결/권한 검토가 필요. **현재 설치된 경로가 아님** |
| B. 제한된 서버용 API/RPC | 현재 Supabase 클라이언트 기반 인증과 통합 가능 | 함수 실행 권한·호출자 검증·권한상승 위험·원자성·배포 API 노출 범위를 반드시 검증. `SECURITY DEFINER`로 임의 해결 금지 |
| C. 일반 이용자에게 테이블 직접 읽기 | 초기 구현 단순 | 미공개/심사/증거 정보가 새어 나갈 위험이 크며 권고하지 않음 |

- 데이터베이스 권한(`GRANT`)과 행 단위 보안(RLS)은 **별개의 방어선**. `anon`/`authenticated` 테이블 접근은 기본 허용하지 않는다.
- 비공개 스키마를 Data API의 공개 스키마 목록에 실수로 등록하지 않도록 확인. 공개 스키마의 모든 테이블에는 적정 RLS·권한을 검증.
- 조회용 뷰 도입 시 권한상승·뷰 소유자 실행/호출자 실행 여부를 검토.
- 함수가 관리자 권한을 상승해서 실행하도록 설계될 경우 **함수 생성 역할, 검색 경로, EXECUTE 기본 권한, 호출자 검증, 요청 범위 제한**을 별도 보안 감사 없이 확정하지 않는다.
- 외부 사용자에게 `service_role` 키/비공개 DB 자격증명/스토리지 서명 키 전달 금지.
- 이번 문서에는 실제 생성 SQL과 확정된 비밀값을 적지 않는다.

## 8. 참고 이미지: 라이선스·내용 검증·철회

### 8.1 저장 정책

- 상품 적용용 참고 이미지와 사용자의 얼굴 원본 사진을 별도 저장 영역/권한/보존 정책으로 분리.
- 이미지 역할(`brand_swatch`, `merchant_swatch`, `applied_reference`, `style_reference` 등)을 변경하지 않음.
- 상점 썸네일·이미지 URL을 **자동으로 원본 이미지 이용 허가**로 간주하지 않는다.
- 비공개 버킷 우선. 파일 형식/크기/총량 제한, 저장 객체 검증, 해시 비교, 권리/만료 확인 필수.
- 등록된 참조 이미지는 **내용 주소나 고유 버전 키**로 고정하고 덮어쓰기 금지. 새 이미지는 새 심사 대상.
- 파일 증거, 소유 상품/옵션, 적용 영역과 허가 목적을 서버에서 매번 연결 검증.

### 8.2 즉시 철회와 일시적 이미지 링크 주의

- 장기 유효한 서명 URL을 브라우저에 반환해 놓고 이미지 권리 철회 시 그 URL이 즉시 무효화된다고 **가정하면 안 된다**. 다운로드용 서명 URL의 별도 유효기간과 캐시가 존재하기 때문이다.
- **초기 권고:** 가상 체험 입력용 참고 이미지는 브라우저에 서명 URL을 전달하는 대신 **서버가 비공개 저장소에서 직접 읽어** 권한·철회·실제 바이트 해시/형식을 검사.
- 관리 화면 미리보기는 별도 짧은 수명/비공개 처리 규칙과 캐시 정책을 검토. 급한 권리 철회 때 이미 발급된 URL까지 완전 삭제 가능하다고 보증하지 않음.
- 실제 모델 요청 직전 **가장 최근 철회 상태 재확인**; 상태를 모르면 실패.
- 객체 해시 불일치, 만료된 사용권, 파일 역할/부위 불일치, 존재하지 않는 원본, 외부 URL만 남은 이미지 → 승인 실패.
- Supabase의 `storage` 시스템 테이블에 임의로 파일 메타를 직접 INSERT/DELETE하지 않고 Storage API를 사용해야 한다.

## 9. 감사, 중복 요청, 데이터 복구

- 감사 사건: 요청 ID, 서버가 확인한 사용자, 실제 관리자 권한, 대상·개정번호, 사건 종류, 검수된 증거 ID, 사유, 변경 전후 상태, 실패/성공 범위, 시각.
- 실제 외부 상품 사이트 HTML·권한 토큰·얼굴 사진/이미지 원본·비밀·긴 증거 텍스트는 감사 로그에 저장하지 않는다.
- 사건 데이터는 변경 불가능하게 관리. 업무 상태가 바뀔 때 업무 사건과 현재 상태를 같은 거래에서 확정.
- 복구 시 **과거 공개본 포인터만 복원해 사용권 철회를 되돌리는 사고를 금지**. 복구 후 현재 철회 세대와 권리 상태를 다시 검증.
- 데이터베이스/스토리지 백업은 비공개 운영 정책에 따르고, 백업 복원·재처리·중복 웹훅/요청이 같은 상품을 두 번 공개하지 않는지 시험.
- 동일 요청의 중복 제출은 요청 ID/대상/행위자 기반 중복 방지로 거절하거나 이전 결과를 재현. 충돌 상황에서 마지막 쓰기가 무조건 승리하면 안 됨.
- 실제 감사 보존기간, 라이선스 자료 삭제기준, 반려 자료 정리 시점은 출시 이전 별도 운영 결정을 요구.

## 10. 단계별 실행 계획: 보호 영역을 한 번에 열지 않는다

### 단계 4가 — 저장 계약과 안전 검증 (DB/배포 변경 없음)
1. 현재 오프라인 승인 사건과 서버 공개본 읽기의 입력/출력 계약, 자료 투영 및 신뢰 경계 문서 확정.
2. `published head`와 `revocation epoch`의 일치/변경/철회 경합을 **메모리/모형 공급자**로 재현.
3. 승인/철회와 조회의 실패·중복·오래된 버전/이미지 불일치를 추가한 무료 테스트.
4. 기존 Face Lab 얼굴 분석·추구미·선택, 스킨케어 추천 및 비실행 합성 검증 회귀.

### 단계 4나 — 스키마·권한 설치 준비 (설계 승인 후, 실제 설치는 별도)
1. 배포 DB 프로젝트와 저장소/운영 배포 연결 **동등성 확인**.
2. 페이스랩 비공개 스키마, 7개 논리 자료의 실제 테이블 수/키/고유 제약/인덱스와 현재 포인터/사건 이력 설계.
3. 서버 조회 방식 A/B 중 선정. 해당 방식의 보안 권한·자격증명·거래 모델 결정.
4. 기존 관리자 회원/역할과 페이스랩 전용 권한의 매핑 및 감사 사건 결정.
5. 비공개 버킷 및 자료 이용권·업로드/원본 검증·철회 정책 확정.
6. 마이그레이션·권한 설치/되돌리기·기존 운영 화면 비영향 검증 계획 작성.

### 단계 4다 — 실제 DB/권한/서버 쓰기·읽기 설치 (**별도 명시 승인 필요**)
1. 확정된 마이그레이션 및 권한 변경, RLS/역할과 비공개 버킷 설치.
2. 실제 관리 심사 사건 기록을 원자적 거래로 저장.
3. 공개본/철회 세대의 **서버 최소권한** 조회 함수 연결.
4. 미인가/인증없음/권한없음/중복/교차 상품/철회/만료/동시성/개인정보 누출 테스트.
5. 스키마 동등성·감사 로그·철회 차단·롤백 검증 후에만 시범 상품 등록 허용.

### 단계 5 — 최소 실상품·관리 화면 (별도 운영 승인)
- 기존 3단계 설계의 립 1종 색상 2개, 하이라이터, 렌즈, 안경 또는 헤어 참고자료 등 **소규모 검수 대상만** 사용.
- 실제 이미지 사용권과 원본 이미지 확보 없으면 **상품 정보만 등록 가능**; 가상 이미지 적용 미지원.
- 상품 관리 목록 → 심사 근거 상세 → 승인/철회 → 감사 기록의 최소 관리자 화면.
- 아직 유료 이미지 호출을 자동으로 활성화하지 않음.

### 단계 6 — 유료 이미지 생성 (별도 비용·품질·권리 승인)
- 정확히 승인된 샘플/허용 횟수/비용 상한/이미지 역할 확인 뒤 제한 검증.
- Face Lab의 얼굴 동일성·수정 범위·참고용 결과 고지·원본 사진 처리 규칙을 그대로 지킨다.

| 영역 분리 | 스킨케어 데이터 0건이어도 Face Lab 자체 자료를 읽을 수 있음 | 기존 `products` 또는 taxonomy 승인 필수 조회 |
| 서버 인증 | 허용된 사용자만 공개본/구독 허용 범위를 조회 | 미인증·타인 세션·권한 없는 회원 |
| 관리자 권한 | 등록/검수/공개/철회 권한이 업무별로 강제됨 | `admin.products.review`만으로 임의 공개 |
| 승인 자료 | 상품·옵션·색상·기능·참고 이미지 모든 필수 근거가 최신 | 하나라도 누락/위조/버전 불일치 |
| 동시성 | 중복 승인/갱신 요청을 하나의 결과로 통일 | 낡은 개정번호, 동시 등록, 일부 거래만 저장 |
| 철회 | 철회 성공 후 새 조회/실행은 해당 후보 차단 | 저장된 룩, 캐시, 이전 승인 기록으로 재사용 |
| 참고 이미지 | 허가된 실제 원본·종류·길이·해시 일치 | 스토리지 유령 객체, 교차 상품, 라이선스 만료 |
| 데이터 노출 | 미공개 심사 기록·원본 파일·감사 자료가 클라이언트에 없음 | 일반 사용자 직접 테이블/RPC 호출 |
| 운영 복구 | 안전한 검증 실패와 되돌리기 절차 존재 | 철회 상태가 백업 복원으로 과거로 회귀 |
| 비용 | 별도 승인 전 유료 호출 0 | 서버 조회 성공을 자동 생성 승인으로 판단 |

자동 테스트의 성공은 실제 RLS·서버·이미지 권리의 검증 완료가 아니다.
보호 영역이 설치된 이후에는 **역할별 허용/거부 실제 DB 테스트와 비공개 버킷 접근 테스트**가 별도로 필수다.

## 12. 주요 미확정 사항과 승인 대상

**이번 문서에서 의도적으로 확정하지 않는 것:**
1. 운영 배포 DB가 과거 조사한 DB와 동일한지.
2. 새 서버용 좁은 DB 역할 자격증명을 도입할지, 제한된 기존 연결을 통해 조회할지.
3. 실제 비공개 스키마·테이블 및 인덱스 설치 SQL.
4. 관리자 권한 매핑/자기 승인 허용 여부와 긴급 철회 담당자.
5. 실제 참고 이미지 사용권 원문 확보 및 저장 위치/보존기간.
6. 운영 호출량·실물 상품 첫 등록 대상/범위 및 유료 이미지 생성 승인.

보호 변경은 대상을 정한 후 사용자 **별도 명시 승인**을 받고 수행해야 한다.
`SECURITY DEFINER`, `service_role`, 임의 `authenticated` 테이블 공개로 권한 오류를 편법 해결하지 않는다.

## 13. 종료 조건과 현재 판정

- **A — 보호 영역 구현 설계 완료:** 현재 코드/권한 경계 파악, 최소 자료 모델, 원자적 심사/철회, 사용자/관리자 서버 조회, 참고 이미지 원본/사용권, 단계별 검증과 승인 항목이 문서화됨.
- **B — 모형 서버 읽기·철회 구현 완료:** 가짜 데이터 원천으로 현재 공개본/버전·철회 세대·접근 차단의 무료 회귀 테스트 통과. **현재 미구현**.
- **C — 실제 DB/관리자/이미지 저장·서버 조회 운영 완료:** 보호 권한/실제 심사·저장/동시성/이미지 사용권 검증이 운영 확인됨. **현재 미구현**.

**다음 즉시 작업은 4가: 비운영 모형 자료 공급자 기반의 '원자적 공개본 읽기와 철회 상태 검사' 구현 및 무료 테스트.**
