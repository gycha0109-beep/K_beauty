# 페이스랩 V2 — 독립 상품·스타일 자료 운영 체계 설계 v1

- 기준일: 2026-10-09
- 저장소 기준: `main@28b40325ef0bca5f3d855da0b6112a887a8dc6a8`
- 작업: 페이스랩 독립 구조 3단계(상품 등록·검토·승인·철회·조회 경계) **설계만**
- 결과물 지위: **미배포·미구현 운영 설계안**. 아래 저장소 이름·권한·상태는 신규 제안이며 실제 운영 데이터베이스에 존재한다는 뜻이 아니다.
- 공통 원칙: 스킨케어 추천은 별도 영역. 기존 `products`, `product_fact_subjects`, 전사 `catalog_taxonomy`의 승인 여부는 페이스랩 상품 사용의 선행조건이 아니다.

## 1. 이번 단계의 정확한 목적

앞선 구현:
- PR #1183: `lib/face-lab-v2/independent-execution-candidate.js`는 상품/옵션/근거 **형식** 및 얼굴 적용 영역의 계약을 무료로 검증한다.
- PR #1184: `lib/face-lab-v2/independent-look-preview-bridge.js`는 위 결과로 기존 합성기에 적용 지시서를 만들지만, `dry_run`을 반환하고 실행 가능한 승인 객체·유료 생성 요청을 **반환하지 않는다**.
- 둘 다 입력 문자열에 `approved`, 검토 근거 형식, 파일 해시 형식이 들어갔다고 실제 소유권·권한·라이선스·파일 내용이 검증됐다고 주장하지 않는다.

이번 3단계는 위 **형식 검증과 실제 승인 자료의 신뢰성 사이의 공백**을 메운다.

진행 범위:
1. 페이스랩 전용 상품과 비상품 스타일 실행 대상의 소유권 및 식별자 관리.
2. 실물 상품별 실제 옵션(색상/호수/크기)과 시각적 속성에 대한 검토 근거 저장.
3. 얼굴 적용 가능 근거, 참고 이미지 이용 허가, 변경 및 즉시 철회 절차.
4. 관리자 등록/검수/공개와 이용자 읽기의 권한 분리.
5. 보호된 실제 조회 경로와 검증 기준 정의.

이번에는 **데이터베이스 생성, SQL 실행, 마이그레이션, RLS/GRANT, API, 인증, 이미지 저장, 실물 상품 등록, 유료 생성 실행을 하지 않는다**.

## 2. 어떤 자료를 관리하는가

| 실행 대상 종류 | 예시 | 실제 옵션 | 화면/실행 성격 |
| --- | --- | --- | --- |
| `product` | 립, 하이라이터, 베이스, 컬러렌즈, 안경 등 | 실제 옵션마다 `faceLabVariantId` 필수 | 검증된 부위·표현/참고 이미지가 있을 때 시각 후보 |
| `style_reference` | 헤어스타일, 수염 스타일 등 | 필수 아님 | 승인된 스타일 참고자료가 있어야 시각 후보 |
| `service` | 커트, 눈썹 관리 등 | 필수 아님 | 우선 실천 안내용. 별도 승인된 시각 자료 없이 체험 가능으로 승격 금지 |
| `color_palette` | 스타일 색 조합 방향 | 필수 아님 | 우선 안내용. 실제 화장품 색상처럼 오해시키지 않음 |

- 유통 상거래의 상품군 분류는 이 영역의 정체성 근거가 아니다.
- `visual-try-on-registry.js`의 실행 유형/적용 부위는 기존 페이스랩 기준으로 재사용한다.
- 상품 종류가 특정 부위를 지원한다는 사실만으로 **그 상품·색상 옵션이 해당 효과를 낸다는 증거가 되지 않는다**.
- 레거시 `product_variant:<productId>:<variantId>`와 신규 `face_lab_variant:<faceLabItemId>:<faceLabVariantId>`는 구분한다. 단순 명칭 변경이나 암묵적 연결은 하지 않는다.

## 3. 저장 장소의 기본안과 범위

**권장 기본안:** 기존 Supabase 인프라 안에 페이스랩 전용 **비공개 논리적 저장 영역**을 두되, 스킨케어 업무 테이블과 외래키를 강제하지 않는다.

이유:
- 공통 회원 인증·감사 인프라는 공유할 수 있다.
- 페이스랩 전용 상품·이미지·승인 범위는 별도 권한으로 통제한다.
- 별도 서비스/데이터베이스 구축은 첫 출시 전에 요구하지 않는다.

이는 구축 **권고안**일 뿐 실제 Supabase 스키마, 노출 설정, 역할, RLS 정책이 확인되거나 승인된 것은 아니다.
설치 전에 실제 배포 서비스의 프로젝트 식별자, 연결 권한, 스키마 노출 목록, 관리자 인증과 파일 저장 접근 방식을 별도로 감사한다.

### 3.1 최소 저장 자료 7종(개념 모델)

아래 이름은 **제안 이름**이며 마이그레이션 파일명이나 실제 테이블이 아니다.

| 논리 자료 | 핵심 필드 | 관계 및 규칙 |
| --- | --- | --- |
| 실행 대상 `face_lab_items` | `item_id`, `kind`, `execution_type?`, `display_name`, `lifecycle`, `record_revision`, `created_at` | 독립 페이스랩 식별자. 비상품 실행 대상을 스킨케어 `products`로 몰아넣지 않음 |
| 실제 옵션 `face_lab_variants` | `item_id`, `variant_id`, `identity_state`, `lifecycle`, `option_axes`, `source_revision` | 실물 상품 하위 식별자. (`item_id`, `variant_id`) 유일. 표시명으로 자동 발급 불가 |
| 색상·표현 사실 `face_lab_appearance_facts` | `item_id`, `variant_id?`, `attribute_key`, `value`, `evidence_id`, `review_revision` | 임의 추측 금지. 속성별 검증 근거·버전 필수. 불명확하면 비워 둠 |
| 적용 부위별 기능 심사 `face_lab_capability_reviews` | `candidate_ref`, `slot_key`, `support_state`, `proof_class`, `evidence_ids`, `decision_revision` | 제품 종류와 별개로 개별 부위/효과를 승인·거부. 거부·상충·미결은 사용 불가 |
| 출처·증거 `face_lab_evidence` | `evidence_id`, `source_kind`, `origin_reference`, `captured_at`, `claim_scope`, `fingerprint`, `review_status` | 공식/판매처/큐레이션 구분. 실제 자료 내용·관찰 근거·권리 범위와 연결; 증거 문자열 자체는 신뢰 근거 아님 |
| 참고 이미지 `face_lab_reference_assets` | `asset_id`, `candidate_ref`, `slot_key`, `role`, `storage_key`, `mime_type`, `size`, `sha256`, `permission_scope`, `license_expires_at?`, `review_revision` | 비공개 저장 위치. 후보/부위/역할/권리/해시 결속. URL 문자열만으로 사용 승인 금지 |
| 승인 이력·공개본 `face_lab_publication_ledger` | `event_id`, `item_id`, `event_type`, `actor_role`, `previous_revision`, `new_revision`, `decision_reason`, `published_revision?`, `committed_at` | 심사/승인/거부/철회/공개 이벤트는 변경 불가능하게 기록. 최신 공개 버전 식별 |

**필수 후속 정합성 판단:**
- `item_id`는 신뢰 가능한 관리 등록에서 발급·고정하며, 삭제 후 다른 상품에 재사용하지 않는다.
- `variant_id`도 같은 상품 내에서 재사용하지 않는다. 색상 이름만 바뀌었다면 근거와 함께 변경 버전을 기록한다.
- 외부 상품번호·판매처 URL·스킨케어 Product Fact Subject는 선택적 외부 대응표의 **입력 후보**일 뿐 실행의 필수 외래키가 아니다.
- 실제 운영 구조에서는 위 7종을 별도 테이블로 나눌지, 버전 고정된 일부 하위 행으로 묶을지 스키마 리뷰에서 결정한다. 처음부터 무제한 범용 속성 저장 구조를 만들지 않는다.
- 사람 얼굴 사진, 개인 추구미, 사용자별 생성 이미지는 위 **상품 관리 저장소에 저장하지 않는다**.

### 3.2 검증 가능한 자료와 미검증 자료의 구분

관리 영역은 아래 차이를 기록해야 한다.

- `source_present`: 출처가 입력됨. **승인 아님**.
- `source_reviewed`: 검토자가 원문/이력 및 인용 범위를 확인함.
- `identity_verified`: 실제 상품과 옵션의 존재 및 정체성 확인.
- `capability_verified`: 특정 후보가 특정 부위에 어떤 표현을 줄지 증거 확인.
- `reference_usage_verified`: 이미지에 **가상 체험 입력으로 활용할 명시적 사용권**이 있음.
- `published`: 현재 버전의 필요한 근거가 모두 유효하여 서버에서 정식 조회 대상.

브랜드 공식 웹사이트에서 본 이미지라 하더라도 상품 사실의 출처와 **이미지 재사용 권한**은 별도로 검증한다.

## 4. 등록·검수·공개·철회 흐름

### 4.1 상태와 역할

업무 역할(개념): `등록 담당`, `검수 담당`, `공개 관리자`, `운영 조회자`, `최종 이용자`.

역할명은 데이터베이스의 실제 권한 역할이나 계정 생성 지시가 아니다.
초기 1인 운영 시에도 등록과 승인 행위는 **서로 다른 절차·감사 이벤트**로 남겨 의도치 않은 자동 승격을 막는다.
특정 데이터에 대해 등록 담당의 자기 승인 허용 여부는 실제 운영 위험 검토 후 별도 확정한다.

    자료 등록(초안)
         ↓
    출처·옵션·효과·이미지 권리 각각 검토
         ↓
    심사 대기 → 반려 / 수정 후 재심사 / 승인
                                     ↓
                            버전 고정 및 공개
                                     ↓
                             정상 조회/사용
                                     ↓
                     근거 만료·오류·권리 철회 감지
                                     ↓
                            즉시 차단·철회
                                     ↓
                          재검토 후 새 버전 공개

초안/심사대기/반려/승인/공개/일시중지/철회의 **상태 전이를 기록**하며, 단순히 화면의 문자열 `approved`로 실데이터를 승격하지 않는다.

### 4.2 승인 단위

1. **실행 대상 정체성:** 대상 종류, 상품명/브랜드, 외부 출처, 중복 등록 여부.
2. **실제 옵션:** 각 색상/호수/모델의 실재성, 해당 상품 소속, 버전.
3. **색상·표현 속성:** 항목별 근거. `Rose`라는 단어를 실제 색값으로 임의 변환하지 않음.
4. **적용 기능:** `candidate_ref + slot_key + proof` 별 검토. 지원 근거가 없는 부위는 제공하지 않음.
5. **참고 이미지:** 상품/색상/부위 결속, 역할, 소유/사용 허가, 만료, 파일 형식과 내용 해시.
6. **최종 공개:** 동일한 심사 버전의 필수 자료만 묶어 공개. 일부만 최신이고 일부는 이전 버전이면 차단.

**전파 규칙:** 상품 등록 승인은 옵션 승인이 아니다. 옵션 승인은 표현 특성·참고 이미지 승인이 아니다. 참고 이미지 승인은 시각적 재현 정확도에 대한 보장이 아니다.

### 4.3 변경 및 철회

- 승인 대상의 이름·옵션·표현 사실·부위 매핑·이미지·사용권 중 하나라도 실질적으로 변경되면, 해당 근거와 의존 공개본의 유효성을 재평가한다.
- 판매 중단은 정책에 따라 노출 중지/철회하되, 이전 상품 ID를 다른 실물 상품에 재사용하지 않는다.
- 이미지 이용 허가 만료/철회, 해시 불일치, 옵션 소속 오류, 근거 철회는 **즉시 이용 중지** 대상으로 처리한다.
- 철회/변경을 감지했는데 캐시·복제본에 종전 `published`가 남았다면 **읽기와 실행 직전 최신 철회 세대값을 확인하지 못하는 동안 사용 금지**.
- 과거 사용자 저장 룩은 자동 삭제하지 않더라도 해당 제품을 새로 적용·재생성하려는 순간 다시 검사한다.
- 감사 기록은 추적 가능하게 보존하되 개인·비밀 데이터 원문을 남기지 않는다. 보존 기간은 별도 개인정보/운영 정책 승인으로 확정한다.

## 5. 권한 체계 — 읽기와 쓰기 완전 분리

| 사용자/프로세스 | 초안 작성 | 심사 근거 열람 | 승인·철회 | 공개 상품 조회 | 비공개 이미지 원본 |
| --- | --- | --- | --- | --- | --- |
| 미로그인 사용자 | 불가 | 불가 | 불가 | 정책적으로 공개된 최소 정보만(초기 기본 불허) | 불가 |
| 로그인 최종 이용자 | 불가 | 불가 | 불가 | 자신의 상품 기능·구독 상태가 허용하는 최소 정보만 | 직접 접근 불가 |
| 등록 담당 | 본인 작업 범위만 | 허용된 출처만 | 불가 | 내부 확인용 | 직접 공개 URL 불가 |
| 검수 담당 | 승인 대상 수정은 별도 절차 | 허용된 근거만 | 검수 의견/심사 기록 | 가능 | 권리 검수에 필요한 최소 범위 |
| 공개 관리자 | 별도 권한 필요 | 감사용 | 승인 공개/철회 | 가능 | 필요 최소 범위 |
| 페이스랩 서버 전용 조회자 | 불가 | 불가 | 불가 | 승인된 공개본 **읽기 전용** | 별도 검증된 서버 로더만 |

위 표는 보안 설계 요구사항이며 **기존 서비스의 실제 권한표로 확인되지 않았다**.

- 신규 페이스랩 자료는 일반 `anon`·`authenticated` 역할에 테이블 직접 읽기/쓰기를 기본 허용하지 않는다.
- 사용자 요청에 들어온 `approvalState`, `sourceVersion`, `evidenceRefs`, `storageKey`, 이미지 URL, 옵션 객체를 신뢰하지 않는다.
- 서버가 사용자를 인증·권한 검사한 다음, 허용된 **상품 ID/옵션 ID/적용 부위만** 받아 관리된 공개본을 다시 조회한다.
- 실제 조회 수단은 비공개 테이블에 대한 최소 권한 서버 접근 또는 제한된 전용 읽기 함수 중에서 보안 리뷰로 결정한다.
- 권한 상승 함수 도입 시, 호출자 검증/검색 경로 고정/행 제한/로그·오류 노출 방지/함수 실행 권한을 별도 검증한다.
- 추천 서비스 전용 DB 역할, 기존 `service_role`, 관리용 `postgres` 접근을 페이스랩 실행 요청의 지름길로 사용하지 않는다.
- 실제 로그인, 구독, 관리자 판정은 기존 서비스의 **확인된 서버 권한 체계**를 따라야 한다. 이번 문서가 인증 계약을 새로 확정하지 않는다.

## 6. 신뢰할 수 있는 운영 조회 계약

개념적 서버 호출 예시(아직 코드 없음):

    readPublishedFaceLabSelection({
      faceLabItemId,
      faceLabVariantId?,
      slotKey,
      userContext        // 외부 입력이 아니라 서버 인증에서 획득
    })

서버 처리 순서:
1. 서버 인증 및 페이스랩 접근 권한을 검사한다. 실패 시 즉시 거절한다.
2. 페이스랩 자료 저장소에서 최신 공개 버전을 직접 조회한다. **스킨케어 추천 DB를 읽지 않는다**.
3. 대상/옵션/부위 소속·현재성·철회 상태 및 공개 버전의 일치 여부를 검증한다.
4. 항목별 색상 속성·기능 승인 근거가 해당 공개 버전에 속하는지 확인한다.
5. 이미지 사용권(용도/기간/범위), 소유 상품/옵션/부위, 비공개 저장 경로와 등록 해시를 확인한다.
6. 검증용 입력을 `validateFaceLabIndependentExecutionCandidate` 및 `composeFaceLabIndependentLookPreview`에 전달한다.
7. 화면에는 최소한의 상품·옵션·미리보기 가능 여부만 반환한다. 내부 심사 원문·비공개 경로·권한 토큰·원본 이미지 자료는 반환하지 않는다.
8. 나중에 실제 가상 이미지 생성 경로가 별도 승인되면 **생성 요청 직전 권한·철회·이미지 실제 바이트 해시를 다시 검사**한다.

### 6.1 사용 상태

| 상태 | 의미 | 화면 처리 |
| --- | --- | --- |
| `available` | 서버에서 실제 승인된 정체성/근거/권한 확인 | 승인된 범위만 표시 |
| `guidance_only` | 관리/서비스/색 조합 안내는 가능하나 시각 이미지 생성에는 부적절 | 이미지 적용 버튼 미노출 |
| `not_reviewed` | 등록은 됐지만 필수 증거 미심사 | 상품 적용 불가 |
| `temporarily_unavailable` | 자료/권한/이미지 검증 정보 부족 또는 오류 | 사용 불가, 사유는 과도하게 노출하지 않음 |
| `revoked` | 상품·옵션·근거·사용권 철회 | 신규 적용·재실행 차단 |
| `not_found` | 게시/조회 대상 부재 | 존재 여부 유추를 막도록 응답 차등을 검토 |

**핵심 경계:** 위 서버 판단의 `available`과 기존 합성기의 `status: ready`는 서로 다르다. 현재 무료 합성 결과의 `dry_run`도 **실제 승인된 운영 상품**을 뜻하지 않는다.
신뢰된 서버 조회와 유료 생성 승인 단계를 혼동하지 않는다.

### 6.2 경합·오류 대책

- 상품 공개본은 버전이 고정된 단위로 읽는다. 검수 중 혼합 버전이 한 화면에 출력되면 실패 처리.
- 중복 등록/동일 ID 다중 수정은 고유 제약과 기대 버전 비교로 막는다.
- 심사 직후 철회되는 경합을 대비해 별도 철회 세대/현재 공개 상태 재검사가 필요하다.
- 외부 출처 중단, 이미지 권리 만료, 메타데이터 손상, 비공개 파일 미조회는 **임의 사진·과거 캐시로 대체하지 않고 실패**.
- 권한 실패를 해결하기 위해 기존 스킨케어 상품 API, 관리자 계정, 브라우저 직접 파일 접근으로 우회하지 않는다.
- 운영 감사 로그에는 누가 무엇을 승인·철회했는지 남기되 개인의 얼굴·사진·비밀 키·파일 원문·과도한 상품 출처 원문은 남기지 않는다.

## 7. 참고 이미지 검증을 두 단계로 구분

**지금 있는 2단계 무료 코드가 검사하는 것:**
- 이미지의 후보/부위 연결, 역할 및 라이선스 상태 문자열
- 보안 저장 경로 형식, 바이트 수·파일 종류·해시 문자열 형식
- 이미지 목록의 중복·개수·순서

**실제 운영에서 추가해야 하는 것:**
- 승인 관리 저장소에서 서버가 신뢰할 자료 레코드를 재조회
- 권리 문서의 실제 근거, 허가된 처리 용도, 만료 및 철회 상태 검사
- 비공개 저장소의 정확한 객체를 서버가 조회하고 실제 파일 종류/길이/해시 일치 확인
- 사용자 얼굴 사진과 참고 이미지는 역할·접근 정책·개인정보 보관 기준을 분리
- 최종 모델에 보내기 전 크기/합계 용량 제한과 사용 범위 재확인

사용자에게 임의 외부 URL, 화면용 상품 썸네일, 상점 HTML 링크를 입력으로 받아 가상 체험 참고 이미지로 직접 전용하지 않는다.

## 8. 초기 관리 화면: 단순하게 시작

1인 운영을 고려하여 첫 버전에는 복잡한 대시보드 대신 **등록 목록 → 상세 근거 검토 → 공개/보류/철회 → 감사 이력**만 제공하도록 권고한다.

최소 관리자 항목:
- 대상 종류와 이름/브랜드, 실제 옵션 목록
- 옵션별 식별 근거와 검토 상태
- 부위별 적용 기능 승인·거부 및 근거
- 색상/표현 속성별 근거
- 참고 이미지 권리/사용 기간/파일 검증 결과
- 작성자·검토 시점·승인자·버전·철회 사유

출시 초기에 무작위 크롤러 결과를 자동으로 실제 상품 승인하지 않는다.
대량 수집·자동 매칭·유사 옵션 병합·AI 자동 심사 등은 이 절차의 검증 결과가 나온 뒤 확장한다.

### 8.1 첫 검증 대상의 범위

대표 조합 권고:
- 립 제품 1개와 서로 다른 실제 색상 옵션 2개
- 하이라이터 1개와 검토된 발색 속성
- 컬러렌즈 1개 및 실제 모델/색상 확인
- 안경 1개 또는 헤어 스타일 참고자료 1건
- 안내만 가능한 관리 서비스 1건

**모두 제안된 검증 규모다. 실제 브랜드·상품·이미지 사용권이 확보됐다는 뜻이 아니며, 임의 상품을 운영 자료로 발행하지 않는다.**

## 10. 필수 검증 목록

- [ ] 스킨케어 상품 테이블·통합 분류가 비어도 독립 페이스랩 운영 계약이 성립한다.
- [ ] 동일 상품/옵션이 중복 등록되지 않으며 ID가 재사용되지 않는다.
- [ ] 옵션 소속이 다른 상품으로 변경돼도 해당 부위에서 적용하지 못한다.
- [ ] 근거가 없는 색상·광택·발색 추정은 승인되지 않는다.
- [ ] 종류의 기본 적용 부위와 개별 상품의 적용 증거를 구분한다.
- [ ] 잘못된 부위·지원되지 않는 실행 후보를 거부한다.
- [ ] 표시 이름이 같아도 다른 상품·옵션을 합치지 않는다.
- [ ] 후보/부위가 다른 이미지 연결은 실패한다.
- [ ] 이미지의 저작권·라이선스/목적/기간이 불명확하면 거부한다.
- [ ] 사용 허가 철회/파일 해시 불일치/출처 변경 후 기존 공개본 재사용을 막는다.
- [ ] 읽기 중 공개 버전이 바뀌면 혼합 버전 결과 대신 안전 실패한다.
- [ ] 일반 이용자는 초안·심사 자료, 관리자 액션, 비공개 원본 파일을 읽거나 수정할 수 없다.
- [ ] 관리 담당자는 자신에게 부여되지 않은 승인/철회 권한을 사용할 수 없다.
- [ ] 참고 이미지와 얼굴 사진의 자료 저장/이용 정책이 분리된다.
- [ ] 서비스/색 조합 안내가 상품 이미지 생성 승인으로 자동 승격되지 않는다.
- [ ] 클라이언트가 조작한 `approved`/해시/경로 문자열을 서버가 신뢰하지 않는다.
- [ ] 상품 미준비가 얼굴 분석/추구미/경로 비교 전체를 차단하지 않는다.
- [ ] 유료 생성 호출 0, 구형 페이스랩·스킨케어 추천 회귀 없음.
- [ ] 운영 시 DB 접속/로그/비밀 값이 외부로 노출되지 않는다.

## 11. 이번 설계의 종료 조건

- **가 — 설계 작성 완료:** 위 자료 모델, 역할, 승인/철회 전이, 신뢰 조회 경계, 위험/검증/차후 작업이 설명되며 기존 코드와 충돌이 문서상 해결된다.
- **나 — 무료 순수 코드 구현 완료:** 운영 기록의 유효성·상태 전이·철회 판단이 가짜 자료 테스트에서 재현됨. **이번 작업 범위 밖**.
- **다 — 실제 상품 조회 운영 완료:** 전용 승인 저장소/보안 읽기/이미지 권리 검수/실상품 제한 연결이 검증됨. **이번 작업 범위 밖**.

**남은 결정:** 실제 저장소 스키마와 DB 역할/관리 권한, 배포 환경 동등성, 승인자 분리, 참고 이미지 사용권 판단 책임, 정식 상품 등록 규모. 이 항목은 기존 제품/인증 정책 검토 없이는 '확정된 운영 상태'로 보고하지 않는다.

## 12. 기존 근거와 충돌 방지

- 2026-10-09 독립 구조 설계: `face-lab-v2-p1-d2c-independent-execution-catalog-design-v1.md`.
- 현재 순수 코드 계약: `independent-execution-candidate.js`.
- 현재 합성기 무료 연결: `independent-look-preview-bridge.js`.
- 옵션·색상 세부 불변식: `face-lab-v2-product-variant-shade-authority-v1.md`. 구형 Product Fact Subject를 실제 색상 ID로 해석하지 않는 원칙만 계승.
- 기존 `catalog-reference-resolver.js`의 파일 해시·바이트 검증 구조는 후속 독립 읽기 경계의 **참고 후보**다. 구형 상품 ID/승인 토큰을 그대로 상속하지 않는다.
- 2단계의 `dry_run` 성공만으로 실제 승인 객체를 반환하게 변경하는 작업은 **이번 설계에서 금지**.

**결론:** 현 시점의 최선의 다음 구현은 운영 데이터베이스 변경이 아니라 **3나: 관리 이벤트·자료 버전·승인/철회의 독립 순수 코드 계약 및 무료 회귀검증**이다. 이후 안전성 확인과 별도 승인으로 실제 저장·조회 단계에 들어간다.
