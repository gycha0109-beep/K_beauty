# Premium Hosted Preview Harness Hardening v1

Status: Design only

Base commit: `5dd2c469d223c878a2139d8276b2c4a04c2f6bf3`

Target: Draft PR #38 / `agent/premium-hosted-preview-verification`

## 1. Problem statement

The first Hosted Preview execution attempt stopped with `HARNESS_FAILURE` before any runtime lane executed.

Confirmed harness gaps:

1. The UI journey verifier reads canonical state from selectors or `data-*` attributes that do not exist in the current UI.
2. Fixture-controlled `requiredEvidence` can reduce the mandatory evidence set and create false passes.
3. Google login capture records host, SHA, and path but does not independently prove the authenticated Supabase user, permanent-user status, or Account A/B distinctness.
4. Preflight does not verify actual account identity, OAuth callback completion, Preview protection access, required Preview configuration presence, or live schema compatibility.
5. KO/EN semantic comparison omits canonical reason codes and confidence or uncertainty semantics.
6. Static contract verification did not detect these runtime-assurance gaps.

This hardening must repair the verifier without changing Premium runtime behavior.

## 2. Scope

### In scope

- Hosted Preview verifier code

- fail-closed preflight contracts
- canonical evidence extraction

- documentation and work log

### Out of scope

- Fault Preview creation

## 3. Design principles

1. Runtime evidence must be derived from trusted application outputs, not fixture-declared optional fields.
2. Fixtures may provide interaction instructions and expected scenario identity, but may not define which evidence is mandatory.
3. Authentication identity must be resolved through Supabase using the authenticated session, then stored only as SHA-256 identifiers.
4. Every evidence object must include provenance: source, route, timestamp, target host, deployment SHA, and schema version.
5. Missing or ambiguous evidence is a harness failure, not a pass.
6. UI text alone is not sufficient for canonical equality because KO and EN differ by translation.
7. The verifier must distinguish application failure from harness inability to observe the application.
8. No secret, cookie value, token, email, OAuth code, or raw photo may enter artifacts.

## 4. Canonical evidence architecture

### 4.1 Evidence sources

Use three evidence layers.

#### Layer A — Auth identity evidence

Obtained immediately after login from the authenticated Supabase session:

- `userIdHash`
- `isAnonymous`
- `provider`
- `authenticatedAt`
- `targetHost`
- `deploymentSha`
- `finalPath`

The raw user ID must remain in memory only and must never be written.

#### Layer B — Network canonical evidence

Playwright observes the application-owned API responses generated by the user journey.

Allowed extraction targets:

- response status
- public error or reason code
- locale
- snapshot fingerprint
- report, snapshot, and decision-bundle versions
- canonical policy statuses
- canonical reason-code sets
- confidence or uncertainty bands
- consistency verdict
- selected product identifiers intended for the client
- fallback flags

The verifier must reject complete report-body artifact persistence. It may derive a normalized evidence projection in memory and write only that projection.

#### Layer C — UI projection evidence

The browser independently confirms that the UI renders the expected visible state.

UI checks must use existing accessible roles, labels, headings, stable visible text keys, or already-present stable attributes. The harness must not assume nonexistent attributes.

UI evidence confirms projection; network evidence supplies canonical identity. A lane passes only when both agree where both are available.

### 4.2 Mandatory canonical evidence schema

The mandatory schema is defined in verifier code and cannot be reduced by fixtures.

Required fields for normal KO/EN lanes:

- `locale`
- `functional.status`
- `functional.reasonCodes[]`
- `routine.status`
- `routine.reasonCodes[]`
- `condition.status`
- `condition.reasonCodes[]`
- `consistency.verdict`
- `consistency.reasonCodes[]`
- `confidence.band`
- `uncertainty.flags[]`
- `fallback.flags[]`
- `topPick.productId`
- `snapshot.fingerprint`
- `versions.report`
- `versions.snapshot`
- `versions.decisionBundle`

Scenario-specific fields are additive. Fixtures cannot remove the base schema.

### 4.3 Provenance

Each field group records one of:

- `network-response`
- `saved-report-reentry`
- `ui-projection`

If a mandatory field has no trusted provenance, the lane fails with `HARNESS_FAILURE`.

## 5. Login evidence hardening

### 5.1 Capture flow

After the user completes Google login:

1. Confirm final origin equals the selected Preview origin.
2. Resolve the authenticated Supabase session in browser context.
3. Call Supabase `getUser()` or the equivalent authenticated user endpoint.
4. Require a valid user ID.
5. Require `is_anonymous === false`.
6. Require Google provider evidence.
7. Hash the user ID in memory.
8. Write storage state separately from privacy-safe login evidence.
9. Record host, exact deployment SHA, final path, capture time, and user hash.

### 5.2 Cross-account constraints

Preflight requires:

- Account A and B evidence both present
- both evidence files target the current host and SHA
- both users permanent
- both user hashes non-empty
- user hashes different
- storage state authentication resolves to the same hash recorded in the evidence file

A stale storage state or copied evidence file must fail.

## 6. Preflight hardening

Preflight becomes a read-only gate with these checks.

### 6.1 Deployment

- HTTPS Preview URL
- exact expected host
- exact expected SHA
- non-Production environment
- Preview protection access already available to the browser or explicit bypass supplied locally
- redirect remains on the expected origin after protection handling

### 6.2 Authentication

- both storage states parse
- both sessions resolve through Supabase
- evidence hashes match resolved identities
- both accounts are permanent and distinct
- OAuth callback round-trip evidence exists

### 6.3 Runtime configuration

Without exposing values, require successful runtime probes for:

- public Supabase configuration
- authenticated user endpoint
- Premium entry route
- full-report session endpoint
- expected saved-report table and required columns through the authenticated contract
- required migration behavior, tested by schema-capability probes rather than migration-name metadata alone

Preflight must not use Service Role.

### 6.4 Fixture readiness

Require:

- normal photo
- fallback photo
- KO action fixture
- EN action fixture
- selected product case
- not-in-db case
- mixed case
- duplicate-axis case
- finalized-conflict payload
- expected route and stable interaction selectors

All referenced paths must exist. Fixture schema must reject unknown keys and unsupported actions.

## 7. UI journey hardening

### 7.1 Remove fixture-controlled evidence policy

Delete `requiredEvidence` or equivalent fixture authority.

The verifier owns mandatory fields. A fixture may contain:

- start route
- ordered actions
- expected scenario ID
- expected visible projection keys
- optional timeout within a bounded range

### 7.2 Network observer

Install response listeners before the first action.

Capture only application-owned responses from approved routes, such as:

- `/api/analyze`
- `/api/full-report`
- `/api/full-report/session`

Reject:

- responses from unexpected origins
- missing expected response
- multiple ambiguous canonical responses without a deterministic selection rule
- non-JSON success where JSON is required

Normalize the allowed public response fields into the canonical evidence schema.

### 7.3 UI projection adapter

Add a repository-specific adapter based on the actual current DOM.

The adapter must:

- use accessible roles and stable UI structure first
- centralize selectors in code rather than fixture-controlled arbitrary selectors for canonical evidence
- return visible projection states only
- fail when a required section is not present
- never infer a canonical reason code from translated prose

Reason codes, fingerprints, versions, and product IDs must come from network or saved-report evidence, not guessed from text.

### 7.4 Cross-source assertion

For each lane:

- UI policy section visible
- UI visible status corresponds to the normalized network canonical status
- saved reentry fingerprint equals original fingerprint when applicable
- product ID shown by UI equals canonical product ID when the UI exposes it

If the UI cannot expose a required projection, classify as `UI_PROJECTION_FAILURE`. If the harness cannot locate a trustworthy source, classify as `HARNESS_FAILURE`.

## 8. KO/EN semantic parity

Compare normalized canonical evidence, not translated strings.

Mandatory equality:

- functional status
- functional reason-code set
- routine status
- routine reason-code set
- condition status
- condition reason-code set
- consistency verdict
- consistency reason-code set
- confidence band
- uncertainty flag set
- fallback flag set
- top-pick product ID
- snapshot fingerprint when the same canonical input is expected to produce the same snapshot
- report, snapshot, and decision-bundle versions

Locale itself must differ as expected and must not alter stored-report authority on reentry.

Arrays compare as normalized sets unless order is contractually meaningful.

## 9. Scenario contracts

### selected-product

Must show that a DB-known current product is preserved with its canonical product identity and contributes only through permitted policy inputs.

### not-in-db

Must preserve unknown-product identity, uncertainty, and non-causation. No known product ID may be invented.

### selected-plus-not-in-db

Must preserve both rows independently and prevent attribution leakage.

### duplicate-axis

Must provide actual canonical evidence that the duplicate functional axis is detected or constrained according to the current runtime contract. Fixture presence alone cannot pass.

### photo-fallback

Must prove:

- photo insufficiency or fallback flag present
- no fabricated photo observation
- survey authority retained
- canonical output remains internally consistent
- save and reentry preserve fallback semantics

## 10. Contract-verifier expansion

Add pure synthetic tests that fail the old design and pass only the hardened design.

Required tests:

1. fixture omits mandatory evidence — fail
2. fixture attempts to reduce required evidence — fail
3. nonexistent UI selector — fail
4. network canonical response missing — fail
5. UI and network status disagree — fail
6. KO/EN reason codes differ — fail
7. KO/EN confidence differs — fail
8. login evidence hash does not match current session — fail
9. Account A and B hashes equal — fail
10. anonymous account — fail
11. stale host or SHA evidence — fail
12. forged login evidence without resolved session — fail
13. raw user ID, email, token, cookie, or full report appears in artifact — fail
14. source-session raw value appears in artifact — fail
15. every required lane is present with trusted provenance — pass

The contract verifier must test negative behavior, not just successful helper calls.

## 11. Failure taxonomy

Use these distinctions:

- `HARNESS_FAILURE`: verifier cannot establish trustworthy evidence
- `OAUTH_FAILURE`: OAuth flow or identity resolution fails
- `PRECONDITION_FAILURE`: required environment, fixture, host, or SHA absent
- `UI_PROJECTION_FAILURE`: canonical response exists but UI projection is absent or contradictory
- `ENGINE_OUTPUT_FAILURE`: canonical response violates the policy contract
- `LOCALE_FAILURE`: KO/EN canonical semantics differ
- `AUTH_BOUNDARY_FAILURE`: identity or ownership boundary violated
- `PERSISTENCE_FAILURE`: save or DB evidence invalid
- `IMMUTABILITY_FAILURE`: finalized snapshot or prior report mutated
- `ERROR_HANDLING_FAILURE`: controlled failure leaks internals or produces false success

The first failing lane stops dependent lanes, but independent preflight findings may be aggregated before writes begin.

## 13. Validation plan

### Static

- syntax check for every changed script
- Hosted Preview hardening contract verifier
- existing Premium browser journey contract verifier
- existing route, reentry, integrated-evaluation, and policy verifiers
- architecture guard
- production build
- `git diff --check`

### Independent verification

Use an exact-head temporary validation branch or PR.

Required result:

- all negative harness tests pass by correctly rejecting invalid evidence
- all prior regression verifiers pass
- no runtime, DB, Auth, RLS, deployment, or Production change

### Runtime boundary

Static PASS does not equal Stage 10 PASS. After hardening, actual Hosted Preview execution still requires:

- exact-head READY Preview
- safe Preview protection access
- dedicated Account A/B
- non-personal normal and fallback image fixtures
- independent Fault Preview for safe-5xx

## 14. Acceptance criteria

Hardening implementation is complete only when:

1. fixture files cannot weaken mandatory evidence.
2. no nonexistent UI attribute is assumed.
3. canonical semantics are obtained from a trusted application-owned source.
4. UI projection is independently cross-checked.
5. login evidence proves the current permanent Supabase user and exact host/SHA.
6. Account A/B distinctness is enforced.
7. Preflight verifies live capabilities rather than metadata only.
8. KO/EN comparison includes reason codes, confidence, uncertainty, fallback, product identity, and versions.
9. negative synthetic tests cover forged, stale, absent, and contradictory evidence.
10. artifacts contain no raw identities or credentials.
11. existing verification stack and build remain green.
12. Critical and Important review findings are zero.

## 15. Stop conditions

Stop implementation and request a separate approval when:

- trusted canonical evidence is not available from existing client-visible API responses or saved-report responses
- application runtime or UI must be changed to expose test-only state
- DB schema, RLS, Auth, Vercel, or Supabase configuration must change
- Production access is required
- Service Role would be required
